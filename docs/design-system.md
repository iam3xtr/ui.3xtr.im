# Дизайн-система Trickster

Ссылки B1–B4 в этом документе — исторические идентификаторы внешних задач
кабинета, исключённых из локальных этапов UI Kit:
[B1 — #24](https://github.com/iam3xtr/get.3xtr.im/issues/24),
[B2 — #25](https://github.com/iam3xtr/get.3xtr.im/issues/25),

Полные постановки и зависимости перенесены в эти Issues.

Этот документ — единственный источник визуального и компонентного контракта
для личного кабинета Trickster. Он описывает, как выглядят и ведут себя общие
элементы: токены, оболочка приложения, примитивы раскладки, формы, состояния,
слои и контент-паттерны.

Документ живёт в репозитории UI Kit, потому что кит — эталонная реализация
этого контракта. Потребляющие приложения ссылаются на него и не заводят
собственных копий; в `get.3xtr.im` за интеграцию отвечает
`docs/design-system.md` того репозитория, где описаны процедура
синхронизации, реальные маршруты, permissions и план проверок приложения.

История изменений — в `CHANGELOG.md` потребляющего приложения. Рабочие задачи —
в `.plan` и `.todo`.

## Статус документа

Документ описывает **действующий** контракт, а не целевой. Часть контракта
объявлена, но не реализована в CSS — такие места помечены явно и сведены в
раздел «Расхождения контракта и реализации». Не полагайтесь на объявленный
класс, не проверив его наличие в `src/styles/trickster-buefy.scss`.

Переработка контракта идёт по `.plan` (эпик «Миграция Trickster UI Kit на
компоненты личного кабинета»). Пока этап Stage A3 не закрыт, часть правил
ниже описывает ручные эквиваленты того, что должно стать штатным
Buefy-компонентом.

### Планируемая поставка A11 (ещё не действующий контракт)

После Stage A11 визуальная часть контракта переедет в
[`iam3xtr/ui`](https://github.com/iam3xtr/ui), npm-пакет `@iam3xtr/ui`:
tokens, CSS/SCSS-тема, логотип и shared SVG/loader assets. Переносимый
Vue-слой станет отдельным пакетом
[`iam3xtr/vue`](https://github.com/iam3xtr/vue) / `@iam3xtr/vue`: общие
компоненты и framework-level composables для UI-состояний, фокуса и overlays.

В `@iam3xtr/vue` не входят API, Pinia stores, RBAC, router, fixture-данные,
локали мастера, тарифная/доменная политика и product URLs. До фактического
переезда источники истины и entrypoint остаются локальными, как описано ниже;
будущие `packages/ui` и `packages/vue` пока не подключены как сабмодули.

### Планируемая производительность поставки A11 (ещё не реализовано)

Аудит существующего `dist` показал единый initial JS chunk и единый CSS chunk:
в `router.js` все экраны статически импортированы, а `Icon.vue` загружает
все custom SVG через `import.meta.glob(..., { eager: true })`. Это не
действующий API-контракт и не разрешение менять entrypoint без отдельной
задачи; ниже зафиксирован обязательный ориентир для миграции в пакеты.

- Маршруты и редкие тяжёлые поверхности (мастер, kit showcase,
  административные и auth-экраны, формы/модалки) должны загружаться через
  dynamic import. Группировать chunks следует по домену, а не создавать
  отдельный chunk для каждого мелкого компонента.
- `@mdi/font/css/materialdesignicons.css` сейчас поставляет полную таблицу
  классов и полный MDI webfont. До первого package release нужно построить
  и проверить subset из фактически разрешённых MDI-имён, сохранив совместимый
  контракт `b-icon`; отсутствие иконки в subset должно давать проверяемую
  ошибку сборки, а не тихую подмену.
- Custom SVG registry нужно сделать lazy. Это небольшой выигрыш при нынешних
  26 SVG, но требование не даёт будущему набору vendor/model icons попасть в
  initial JS целиком.
- Полная тема CSS остаётся единожды подключённым глобальным контрактом.
  Code splitting маршрутов уменьшает JS, но сам по себе не должен обещать
  сокращение initial CSS; CSS-бюджет оптимизируется прежде всего MDI subset.
- Полная регистрация `app.use(Buefy)` может быть заменена selective imports
  только после инвентаризации реально используемых компонентов, обновления
  Buefy-first реестра и smoke/component tests. Нельзя убрать компонент из
  initial runtime, если он нужен shell или первому маршруту.
- Перед выпуском `@iam3xtr/ui`/`@iam3xtr/vue` измерять initial и lazy chunks
  в raw, gzip и Brotli, проверять загрузку первого маршрута и редкого
  маршрута, и установить budget в library/kit CI. Базовые цифры аудита
  2026-09-15: 842 KB JS / 1.22 MB CSS raw; 186 KB JS / 102 KB CSS Brotli;
  MDI `woff2` — 403 KB raw и около 395 KB Brotli.

## CSS и темы

### Единственный entrypoint

Приложение подключает тему одной строкой:

```js
import './styles/trickster-buefy.scss'
```

Bulma конфигурируется через `@use "bulma/sass"` внутри
`trickster-buefy.scss`. Параллельного Tailwind- или Buefy-CSS entrypoint нет,
и `buefy/dist/css/buefy.css` не подключается.

Стили живут только в `trickster-buefy.scss`. Блоков `<style>` в
`.vue`-компонентах кита нет; в потребляющем приложении их наличие — временное
состояние, снимаемое этапом Stage B3.

### Тема

Тема переключается атрибутом `document.documentElement.dataset.theme`
(`light`/`dark`). Дублирующих классов `theme-light`/`theme-dark` в ките нет —
CSS-контракт целиком построен на `[data-theme]`-селекторах в
`trickster-buefy.scss`.

**Известная вспышка чужой темы.** `App.vue` читает сохранённое предпочтение
(`localStorage['trickster-theme']`) и `prefers-color-scheme` и применяет
`dataset.theme` в хуке `onMounted` — то есть уже после первого рендера Vue,
а не раньше. `index.html` не содержит inline-скрипта, применяющего тему до
монтирования, поэтому при `dark`-предпочтении возможна кратковременная
вспышка светлой темы до монтирования приложения. Исправление (inline-скрипт
в `index.html`, как в остальных доках этого раздела ранее заявлялось) не
входило в scope ни одной из задач A3.1–A3.9 — см. «Расхождения контракта и
реализации».

Цветовые custom properties объявляются в селекторах светлой и тёмной темы.
Типографика, отступы, геометрия и motion объявляются в `:root`.

### Токены

Новые и изменяемые стили используют только `--tr-*`.

| Категория | Основные токены |
|---|---|
| Brand | `--tr-primary`, `--tr-primary-hover`, `--tr-primary-active`, `--tr-primary-soft`, `--tr-primary-border` |
| Поверхности | `--tr-app-bg`, `--tr-sidebar-bg`, `--tr-topbar-bg`, `--tr-surface-1/2/3`, `--tr-surface-hover` |
| Текст | `--tr-text`, `--tr-text-strong`, `--tr-text-muted`, `--tr-text-subtle` |
| Границы | `--tr-border`, `--tr-border-soft`, `--tr-divider` |
| Семантика | `--tr-success`, `--tr-info`, `--tr-warning`, `--tr-danger` и пары `*-soft`/`*-border` |
| Поля | `--tr-input-bg`, `--tr-input-placeholder` |
| Типографика | `--tr-font-family`, `--tr-font-size-*`, `--tr-font-weight-*`, `--tr-line-height-base` |
| Отступы | `--tr-space-1/2/3/4/5/6/8/10/12` |
| Геометрия | `--tr-radius-*`, `--tr-sidebar-width`, `--tr-topbar-height`, `--tr-content-max-width` |
| Эффекты | `--tr-shadow`, `--tr-overlay`, `--tr-transition-fast/normal/slow` |
| Слои | `--tr-z-content`, `--tr-z-sticky-header`, `--tr-z-overlay`, `--tr-z-sidebar`, `--tr-z-dropdown`, `--tr-z-modal`, `--tr-z-toast` — см. «Z-index и stacking» |

Семантические цвета тёмной темы имеют отдельные контрастные значения. Текст на
мягких warning/danger поверхностях использует `--tr-warning-text` и
`--tr-danger-text`, а не основной accent без проверки контраста.

Хардкод-цвета, произвольные пиксельные значения и произвольные `z-index`
контрактом не допускаются: если подходящего токена нет, добавляется токен.

### Типографика и радиусы

Основной стек:

```text
"Inter", -apple-system, BlinkMacSystemFont, "Segoe UI", Helvetica, Arial, sans-serif
```

Отдельный web-font для `Inter` не загружается — используется установленный в
системе шрифт или следующий доступный fallback. Иконочный шрифт Material
Design Icons остаётся отдельным ресурсом.

Bulma `$radius-*` настроены в `0`, чтобы базовые контролы сохраняли принятую
прямоугольную геометрию; собственные элементы задают `--tr-radius-*` явно.
Глобальные Bulma radii нельзя менять без проверки форм, таблиц, dropdown и
модальных окон.

## Иконки

**Правило.** UI-иконки берутся из Material Design Icons. Собственная SVG
допустима только тогда, когда у MDI нет эквивалента, и по факту это ровно две
категории: **иконки вендоров LLM и иконки моделей**. Каждая собственная иконка
обязана иметь запись в реестре ниже с обоснованием; иконка без записи в набор
не входит.

Основание правила: в MDI 7448 иконок, и она покрывает весь служебный слой,
включая полную семью состояний робота (`robot`, `robot-angry`,
`robot-confused`, `robot-dead`, `robot-excited`, `robot-happy`, `robot-love`,
`robot-off`). Вендорских иконок в MDI нет ни одной — `openai`, `anthropic`,
`xai`, `mistral`, `gemini`, `yandex` не находятся.

### Реестр собственных иконок

| Группа | Состав | Обоснование |
|---|---|---|
| Вендоры LLM | `anthropic`, `cerebras`, `cohere`, `deepseek`, `fireworks`, `gemini`, `gigachat`, `google`, `grok`, `groq`, `ionos`, `jina`, `mistral`, `nvidia`, `openai`, `openrouter`, `perplexity`, `sambanova`, `scaleway`, `together`, `xai`, `yandex` | Брендовые знаки, в MDI отсутствуют |
| Fallback вендора | `brain` | В MDI есть `mdi-brain`, но вендорский слот должен рендериться одним компонентом: иначе fallback приходит другим набором, с другим размером и базовой линией |
| Виды моделей | `kind-chat`, `kind-embedding`, `kind-rerank` | Предметные понятия продукта, прямого эквивалента в MDI нет |

Итого 26 иконок. Всё остальное — MDI.

Не являются иконками и в набор не входят:

- состояния чекбокса и радиокнопки — это контрол, используется `b-checkbox`;
- `bars-scale-fade` — инлайновый спиннер приложения (вставлялся вручную 30
  раз в 29 компонентах) — поглощается единым компонентом `Loader`, см. раздел
  ниже, и как отдельная SVG-иконка не переносится.

Карта соответствия «имя из набора приложения → MDI-имя» для всех иконок,
уходящих на MDI, и решение по каждому из 114 файлов набора приложения — в
[`agent-migration-guide.md`](agent-migration-guide.md#12-карта-соответствия-иконок-набор-кабинета--mdi).
Каждое MDI-имя там проверено на существование в установленном `@mdi/font`.

Набор синхронизируется в приложение из кита один-в-один. Добавление иконки в
набор — изменение контракта: сначала запись в реестре с обоснованием, затем
файл.

Декоративная иконка получает `aria-hidden="true"`; смысловая кнопка имеет
доступное имя независимо от иконки.

### Цвет

Каждый файл набора (`src/assets/icons/**/*.svg`) задаёт `fill="currentColor"`
на корневом `<svg>` и не переопределяет `fill` у дочерних элементов —
собственная иконка красится как текст рядом с ней. `Icon.vue` не переопределяет
это через CSS: правило `.tr-icon` в `trickster-buefy.scss` — `fill:
currentColor`, а не захардкоженный `--tr-text`, поэтому обёртка `has-text-*`
(или любой контекст, меняющий `color`) перекрашивает иконку одинаково в
светлой и тёмной теме. Захардкоженных `fill="#…"` в наборе нет; `has-fill-*`
классов в ките нет и не заводится — цвет управляется исключительно через
`color`/`has-text-*`.

## Загрузчик

Индикация загрузки — один компонент `Loader` с анимированным логотипом и
тремя размерами. Собственные спиннеры, вставленные по месту, контрактом не
допускаются.

| Размер | Где | Поведение |
|---|---|---|
| `inline` | Внутри кнопки или строки текста | По высоте текста, не блокирует, не меняет высоту строки |
| `section` | Внутри карточки, панели, области списка | Центр области по обеим осям |
| `screen` | Состояние всего приложения | Полная высота вьюпорта (`100dvh`) |

Правила:

- **Центрирование по обеим осям.** Контейнер использует
  `display: grid; place-items: center` и наследует `min-height` от области.
  Центрирование только по горизонтали с прижатием к верху — дефект, а не
  вариант.
- **Тема.** Логотип наследует цвет от контекста через `currentColor` с разной
  прозрачностью. Захардкоженных цветов в SVG нет.
- **Reduced motion.** SMIL-анимация не отключается CSS-медиазапросом, поэтому
  при `prefers-reduced-motion: reduce` показывается статичный вариант
  логотипа. Индикатор остаётся видимым и понятным.
- **Размер задаётся снаружи.** В SVG остаётся только `viewBox`, без
  фиксированных `width`/`height`.
- **Семантика.** Контейнер — `role="status"`, `aria-live="polite"`, с
  доступным именем; графика — `aria-hidden`. Состояние объявляется один раз,
  а не на каждый кадр.

Загрузка поверх уже отрисованного контента — `b-loading`; скелеты —
`b-skeleton`. `Loader` покрывает случай «содержимого ещё нет».

## Application shell

### Корневая структура

```text
.tr-app
├── .tr-topbar
└── .tr-app-shell
    ├── Sidebar
    └── .tr-main > .tr-page > .tr-page__content
```

- Desktop shell использует grid `200px minmax(0, 1fr)`.
- Ниже `1024px` grid становится одноколоночным, а Sidebar — выдвижной панелью.
- Topbar находится в нормальном потоке и закрепляется через `position: sticky`.
- Auth-маршруты используют отдельную компоновку без Sidebar, как в кабинете
  (`get.3xtr.im/src/App.vue` не рендерит `.tr-app-shell` под `/auth/*`, но
  сохраняет упрощённый `<Navbar />` без пропсов). `App.vue` кита определяет
  auth-маршруты той же проверкой (`route.path.startsWith("/auth/")`) и для
  них рендерит `Navbar` в режиме `minimal` (без переключателя пространства,
  resource-меню, уведомлений и меню пользователя — только логотип) и не
  разворачивает `.tr-app-shell`/`Sidebar`; `RouterView` идёт сразу за
  `Navbar`. `workspaces`/`user` остаются обязательными пропсами и в этом
  режиме (в ките нет отдельного «logged out» состояния — фикстуры загружены
  всегда), `minimal` только прячет разметку, которая их использует.
  `AuthPage.vue`'s `.tr-auth` уже расчитан на ровно один topbar сверху
  (`min-height: calc(100vh - $topbar-height - $space-12)`), поэтому голый
  `Navbar` обязателен, а не просто убран.
- Загрузчик приложения, ошибка сервиса, переключатель пространства, модальные
  окна и тосты остаются отдельными корневыми состояниями.

### Demo-цикл входа и выхода (Task A8.7)

Кит замыкает навигационный demo auth-сценарий без бэкенда, сессии или
токенов:

- «Выйти» из user-menu (`Navbar.vue`, `.tr-dropdown-danger`) генерирует
  событие `logout`, которое обрабатывает `App.vue` (`handleLogout`): вызывает
  `useAuthStore().logout()` (фикстура — сбрасывает `pendingInvite`, без
  сетевого запроса) и переводит на `auth-login`.
- Успешный demo-login (`LoginView.vue`) уже возвращает на `dashboard` (сразу
  или после `WorkspaceSelector`/`auth-invite`, если применимо) — это
  поведение Task A5.10 не менялось.
- Цикл «Войти → Выйти → Войти → …» и прямое открытие любого `/auth/*` URL
  работают одинаково: `App.vue` определяет auth-маршрут той же проверкой
  (`route.path.startsWith("/auth/")`) и рендерит минимальный `Navbar` без
  `.tr-app-shell`/`Sidebar` независимо от того, как маршрут был открыт.
- Кит не вводит понятие «залогинен/разлогинен» как состояние приложения —
  нет флага сессии, охраняемых маршрутов или redirect-guard'ов. Это чисто
  навигационная fixture-петля; реальная аутентификация, токены и
  persistence остаются задачей `get.3xtr.im`.
- Минимальный `Navbar` (`minimal`, только на `/auth/*`) рендерится без
  фона/границы (`.tr-topbar--minimal`) — читается как часть auth-страницы, а
  не отдельная панель продукта. Переключатель темы, который на кабинетных
  маршрутах живёт внутри `.tr-user-dropdown` (недоступного в минимальном
  режиме без user-меню), здесь вынесен в отдельный контрол в правом углу
  (`.tr-topbar__auth-actions`), переиспользуя те же `.tr-theme-toggle`
  классы и `v-model:is-dark`. По умолчанию (без сохранённого
  `trickster-theme` в `localStorage`) тема берётся из
  `prefers-color-scheme` — см. `App.vue`, `onMounted`.

### Режим ширины контента

`route.meta.contentMode` принимает `contained` или `fluid`. Первый центрирует
контент до `--tr-content-max-width`, второй использует полную доступную
ширину. Если metadata отсутствует, применяется `contained`. Новый маршрут
выбирает режим явно — для таблиц, split-view и полноширинных рабочих областей.

Все внутренние вкладки детали агента (`agent`/песочница, `agent-settings`,
`agent-channels`) и коллекции знаний (`knowledge-collection`/файлы,
`knowledge-collection-settings`, `knowledge-collection-statistics`) — `contained`
(Task A8.5): у этих рабочих поверхностей нет table/split-view обоснования для
полной ширины, в отличие от каталогов `/agents/` и `/knowledge/` (без
`meta.contentMode`, наследуют дефолт кабинета) и списочных/split-view
маршрутов вроде `/conversations/**` (`fluid`), которые сохраняют свой режим
без изменений.

### Навигация

Единственный источник metadata основной и административной навигации,
resource links, меню пространства и меню пользователя — один JS-реестр.
Компоненты выполняют маршрутизацию и команды, но не задают порядок, подписи,
иконки или URL пунктов. Resource menu не создаётся в DOM, когда его реестр
пуст. Prefix-aware сравнение сохраняет активным родительский пункт на
вложенных маршрутах.

- fixture-данные платформенные (не per-workspace) и не связаны с доменными

### Мастер создания агента: точки входа (Task A9.2)

Все триггеры «Создать агента» ведут в один route-driven мастер вместо
отдельных локальных форм — именованный маршрут `agent-wizard`
(`/agents/new/:step?`, `meta.contentMode: "contained"`) и его единственный
контроллер `src/components/agents/AgentWizard.vue`:

- **Точки входа**: постоянная кнопка `.tr-topbar__actions` в `Navbar.vue`
  (desktop) и пункт мобильного меню (viewport-независимая, не зависит от
  текущего маршрута), пустой dashboard (`Dashboard.vue`, CTA-карточка вместо
  прежней `{ name: 'agents', query: { create: '1' } }`), каталог `Agents.vue`
  (карточка `tr-entity-card--create` и `empty-action` `ListAsyncState`,
  независимо от фильтра/пагинации/demo-режима) и query-вход
  `/agents?create=1` (`Agents.vue` редиректит на `agent-wizard` вместо
  открытия модалки). Ни один вход не скрывается лимитом/тарифом —
  `Agents.vue` показывает presentation-only пояснение рядом с каталогом на
  тарифе Free, не имитируя permission API и не блокируя кнопку.
- **Auth-маршруты**: минимальный `Navbar` (`/auth/*`) не рендерит
  `.tr-topbar__actions` вовсе — на служебных экранах входа в мастер нет.
- **Контроллер и fallback**: `AgentWizard.vue` — единственное место, которое
  сверяет URL с draft'ом активного пространства (`useWizardStore`, Task
  A9.1): валидный и **достижимый** шаг из адреса синхронизирует draft (прямой
  URL, back/forward), отсутствующий/невалидный/недостижимый шаг не трогает
  draft и просто выправляет адрес на его фактический шаг, а переключение
  пространства показывает собственный draft этого пространства, не читая шаг
  из ещё не обновившегося URL прежнего пространства. «Отменить» удаляет
  только сам draft (`cancelDraft`) — уже созданные им fixture-ресурсы
  (агент/коллекция/источники) остаются, как и требует Task A9.1.
- **Достижимость шага — `isStepReachable`** (`stores/wizard.js`,
  post-review fix): прямой URL вперёд по ещё не заполненным обязательным
  шагам (например, `/agents/new/review` на пустом draft'е) не переводит на
  него — иначе можно было бы молча собрать и сохранить агента с пустыми
  болью/контекстом/правилами (Task A9.3 acceptance: «шаги нельзя молча
  пропустить»). Шаг достижим, когда все предшествующие ему в `WIZARD_STEPS`
  уже пройдены (`isStepComplete`) — практически это только pain/context/rules,
  остальные шаги по умолчанию всегда «пройдены» для `isStepComplete`, так что
  дальнейшие шаги остаются достижимы сразу после rules. Для уже завершённого
  draft'а (`status === "completed"`) достижим только `"review"` — нет
  промежуточного шага, на который стоило бы «расфинишировать» уже
  сохранённого/запущенного агента. Проверка стоит только на этом одном
  вызывающем коде (`syncStepFromRoute`), а не внутри самого `goToStep` —
  внутренние прыжки мастера (`goToStepDirect` у Sandbox/Telegram/Review)
  используют `goToStep` напрямую и не проходят эту проверку, поскольку сами
  двигаются только на уже пройденный более ранний шаг либо на `review` вперёд
  (Telegram «Подключить позже»), чья достижимость зависит от тех же
  pain/context/rules и не может быть нарушена изнутри мастера.
- **`ensureDraft` не подменяет существующий draft** (post-review fix):
  раньше проверял только `continueDraft` (только `in_progress`) и тем самым
  тихо заменял уже завершённый draft новым при любом обращении после
  завершения — например, при обычном browser back/forward с только что
  показанного review-экрана. Теперь `ensureDraft` возвращает любой
  существующий draft независимо от статуса и заводит новый только если для
  пространства вообще нет записи — соответствует Task A9.2's «каждый вход
  открывает тот же draft/шаг, а не отдельную форму» без исключения для
  «completed». Единственное место, которое обязано завести новый draft
  поверх завершённого — явное «Создать следующего агента»
  (`ReviewStep.vue#startNextAgent`), и оно делает это прямым `startDraft`, в
  обход `ensureDraft`.
- **Границы задачи**: A9.2 зафиксировала только вход/маршрутизацию/fallback.
  Содержимое шагов «Боль»/«Контекст»/«Правила» реализовано в Task A9.3 (ниже);
  «Знания»/«Песочница»/«Telegram»/«Проверка и запуск» остаются подписью шага
  без содержимого до Task A9.4 и далее.

### Мастер создания агента: шаги «Боль», «Контекст», «Правила» (Task A9.3)

Первые три смысловых шага (`.plan` таблица «Шаги и обучающий результат»,
строки 1/2/4) — единственные, чьё содержимое реализовано этой задачей;
«Знания» получил своё содержимое следующей задачей (Task A9.4, ниже),
«Песочница» — Task A9.6, «Telegram» — Task A9.7, а «Проверка и запуск» —
Task A9.8 (см. ниже).

- **Прогресс**: `.tr-wizard-progress` — некликабельный список всех семи
  смысловых шагов над карточкой мастера; сознательно не Buefy `b-steps`
  (который умеет кликом по шагу перепрыгивать вперёд) — единственный способ
  сменить шаг остаётся «Назад»/«Далее», чтобы шаг нельзя было пропустить,
  кликнув по прогрессу.
- **Не пропустить молча**: «Далее» неактивна (`:disabled`), пока текущий шаг
  не заполнен — диспетчер `isStepComplete(step, fields)` в
  `src/stores/wizard.js` (плюс `isPainStepComplete`/`isContextStepComplete`/
  `isRulesStepComplete`) решает это по `draft.fields`; шаги за пределами A9.3
  (`knowledge`/`sandbox`/`telegram`/`review`) намеренно считаются пройденными
  — иначе ещё не реализованный UI запирал бы мастер. Ошибки полей показаны
  рядом с полем через штатный `b-field` `:type="is-danger"`/`:message`
  (тот же приём, что `AgentSettings.vue`, «Настройки агента: модель и BYOK»),
  появляются после `blur`/выбора поля, а не при первом рендере шага.
- **Шаг «Боль»** (`agents/wizard/steps/PainStep.vue`): 4 подготовленных
  fixture-сценария (`WIZARD_PAIN_SCENARIOS`) плюс всегда доступная «Другая
  задача» последним пунктом — карточки `.tr-wizard-scenario` (на основе
  `.tr-card`/`.tr-card--interactive`, тот же язык выбора, что
  `.tr-tariff-selector__card--current`). У каждого сценария стабильный `id`
  (переживает back/forward и хранится в `fields.scenarioId`), пример
  клиентского вопроса и ожидаемый результат — без обещания оформления заказа,
  CRM или записи. «Другая задача» требует непустое `fields.customPainDescription`.
  Сетка — `role="radiogroup"`/`role="radio"` с roving tabindex (WAI-ARIA APG,
  post-review fix): Tab входит в группу один раз (пока ничего не выбрано —
  на первую карточку, иначе на выбранную), стрелки перемещают фокус и выбор
  между карточками, как в нативной группе `<input type="radio">`.
- **Шаг «Контекст»** (`ContextStep.vue`): три обязательных текстовых поля
  (`businessDescription`/`customerDescription`/`goalDescription`) и
  редактируемое имя агента (`agentName`) — без обязательного выбора
  пространства или модели. Имя предлагается по выбранному сценарию
  (`WizardPainScenario.suggestedAgentName`) и пересчитывается при смене
  сценария, пока пользователь не отредактирует поле сам — тогда
  `fields.agentNameTouched` останавливает дальнейшую автоподстановку
  (хранится в `draft.fields`, а не в локальном состоянии компонента, чтобы
  уход на «Боль» и обратно не «забыл» о ручной правке).
- **Шаг «Правила»** (`RulesStep.vue`): задача (`task`, текст), стиль
  (`style` — `WIZARD_RULES_STYLE_OPTIONS`), необязательные ограничения
  (`restrictions`), реакция на отсутствие ответа (`noAnswerAction` —
  `WIZARD_RULES_NO_ANSWER_OPTIONS`) и условие связи с оператором
  (`operatorHandoff` — `WIZARD_RULES_HANDOFF_OPTIONS`); последние два
  обязательны. Формулировки не обещают автоматическую передачу диалога —
  режим «спросить оператора» лишь предлагает клиенту связаться с ним
  отдельно. Класс модели и итоговая системная инструкция в экспертной зоне —
  Task A9.5, см. следующий раздел.
- **Подсказки**: `WizardHint.vue` — один переключатель на весь мастер
  (`hintsExpanded` в `AgentWizard.vue`), а не по каждому шагу отдельно.
  Развёрнут по умолчанию для первого агента пространства, компактен для
  последующих — с текстовой ссылкой «Показать подсказки», разворачивающей все
  шаги сразу. «Первый агент» — это `draft.isFirstAgent`, зафиксированный один
  раз в момент `createDraft` (`agentsStore.listByWorkspace(workspaceId).length
  === 0` на тот самый момент), а не пересчитываемое на лету значение
  (post-review fix, Task A9.3): «Знания»/Telegram-шаги заводят реального
  агента (`ensureAgent`/`ensureTelegramChannel`) раньше завершения мастера, и
  пересчёт при каждом входе видел бы уже не ноль агентов у собственного же
  черновика — «Сохранить черновик» с шага Telegram и повторный вход схлопнули
  бы подсказки, хотя онбординг ещё не завершён. `AgentWizard.vue` читает флаг
  при входе в мастер и при смене пространства, не на каждом переходе между
  шагами одного draft'а — иначе разворот подсказок на одном шаге не пережил
  бы переход на следующий.

### Мастер создания агента: экспертные параметры и модели (Task A9.5)

Шаг «Правила» получает две добавки поверх Task A9.3: обязательный, но
необязывающий выбор **класса модели** на основном пути, и вторичную
дисклоузу **«Расширенные параметры»** (`ExpertParameters.vue`) для
температуры, системной инструкции, точной модели каталога и BYOK.
`RulesStep.vue` теперь принимает весь `draft` (не только `fields`) — тем же
приёмом, что `KnowledgeStep.vue` (Task A9.4), потому что классу модели и
экспертной зоне нужны `workspaceId` (capability по тарифу) и `locale`.

- **Класс модели без raw id** (`.plan` "Основной и экспертный режимы...",
  решение 2): `stores/models.js` добавляет `MODEL_CLASSES`
  (`basic`/`advanced`/`power`, только `id` + относительный ценовой tier —
  никакого текста, подписи/пояснения/цена/доступность — scoped RU/EN/ES из
  `src/locales/wizard/**`, см. ниже) и размечает каждый `CatalogModel`
  полем `classId`. `wizardStore.ensureDefaultModelClass` проставляет
  `fields.modelClassId` по `getRecommendedModelClassId(scenarioId)` один
  раз при входе на шаг и никогда не перезаписывает уже выбранное значение —
  отдельного обязательного шага выбора модели по-прежнему нет. Карточки
  переиспользуют `.tr-wizard-scenario*` (та же визуальная семантика выбора,
  что «Боль»); при единственном доступном классе (см. ниже) выбор
  схлопывается в статичную строку вместо трёх карточек с одним вариантом.
- **Fixture-профили тарифов** (`.plan` решение 3): `WIZARD_CAPABILITY_PROFILES`
  в `stores/models.js`, keyed по workspace как `apiKeysByWorkspace`/
  `agentsByWorkspace`, а не отдельным переключателем — `demo` (Free,
  младший: все три класса, но каталог/BYOK недоступны даже в экспертной
  зоне), `trickster` (Superior, расширенный: классы + каталог/BYOK),
  `empty` (единственный доступный класс `basic` — карточек с ложным
  выбором нет). Не тарифная матрица продукта — конкретные цены/права
  решает продукт.
- **Согласованность с каталогом агентов** (`.plan` decision 4:
  «Проверить каталог, фильтры и карточки агентов: младший профиль не
  должен снова требовать узнавать модели в соседнем экране», post-review
  fix): карточка `Agents.vue` и её фильтр «по модели» показывают тот же
  класс модели, что мастер, а не сырое каталожное имя — `getModelClassLabel`/
  `MODEL_CLASS_LABELS` (`stores/models.js`) дают короткий русский лейбл
  вне локализованной экспертной зоны мастера (сам `Agents.vue` не
  локализован, как и весь остальной кит-каталог). Фильтр строится по
  `MODEL_CLASS_IDS`, а не по списку каталожных моделей; сравнение —
  `getModel(modelId)?.classId === modelFilter`. Свободный BYOK-идентификатор
  вне каталога (`provider_model_id`, не входящий в `CATALOG_MODELS`)
  по-прежнему показывается как есть и не относится ни к одному классу — не
  совпадает ни с одним пунктом фильтра, но не пропадает при отсутствии
  фильтра.
- **«Расширенные параметры»** (`ExpertParameters.vue`): малозаметная
  относительно CTA текстовая ссылка (`.tr-wizard-expert__toggle`),
  доступная с клавиатуры (`:focus-visible`) со своей `aria-expanded`;
  свёрнута по умолчанию, состояние — локальный `ref`, а не `draft.fields`
  (незачем переживать back/forward — сами значения внутри переживают через
  `fields`). Раскрывает: температуру (`fields.temperature`), системную
  инструкцию, точную модель каталога (`fields.modelId`, только если
  `capability.allowExpertCatalog`) и BYOK (`useOwnApiKey`/`byokModel`/
  `providerModelId`/`apiKeyId`, только если `capability.allowByok`) —
  переиспользует `ModelSelect.vue`/`ApiKeySelect.vue` без изменений (тот
  же компонент, что и `AgentSettings.vue`). Экспертный режим не даёт новых
  прав — он лишь показывает то, что и так разрешено `getCapabilityProfile`.
- **Системная инструкция — шаблон vs custom**: `generateInstructionTemplate(fields)`
  (`stores/wizard.js`) собирает предпросмотр из `task`/`style`/`restrictions`/
  `noAnswerAction`/`operatorHandoff`, пока `fields.instructionMode !== "custom"`.
  «Написать вручную» переключает в `custom` (текст остаётся редактируемым,
  без дальнейшей автоподстановки), а «Вернуться к шаблону» требует явного
  подтверждения через `modalStore.confirm` (тот же приём, что удаление
  ключа в `AgentSettings.vue`) — шаблон не восстанавливается автоматически
  при правке структурированных полей.
- **Downgrade/capability change** (`.plan` решение 4): если значение в
  `fields` (класс, `useOwnApiKey`, `modelId`) выходит за пределы текущей
  `getCapabilityProfile(workspaceId)`, экспертная зона показывает
  предупреждение (`b-message type="is-warning"`) и ничего не сбрасывает —
  выбор допустимого варианта до запуска остаётся действием пользователя.
- **Locale экспертной зоны** (`.plan` "Ограничения", исключение A9/A10):
  `WIZARD_LOCALES`/`DEFAULT_WIZARD_LOCALE`/`normalizeWizardLocale` в
  `stores/wizard.js`, `draft.locale` — отдельное поле от `fields`, так что
  `setLocale` не трогает пользовательские данные. Тексты — `src/locales/wizard/{ru,en,es}.js`
  (полный одинаковый набор ключей, проверено `tests/unit/locales/wizard.test.js`)
  и `src/locales/wizard/index.js#getWizardDictionary`. Это НЕ кит-wide i18n:
  переведена только новая экспертная поверхность этой задачи (класс модели,
  «Расширенные параметры»), а не весь мастер — остальной текст кита
  по-прежнему фиксирован на русском (`.plan` "Ограничения"). Язык UI не
  зависит от языка инструкции агента: `generateInstructionTemplate` и текст,
  который печатает сам пользователь, локалью не затрагиваются.

### Мастер создания агента: шаг «Знания» (Task A9.4)

`KnowledgeStep.vue` — единственный шаг мастера, которому мало `draft.fields`:
он получает весь `draft` (`workspaceId` + `resources`), потому что сам создаёт
fixture-ресурсы через `useWizardStore()`, а не только патчит поля через
`update`, как Pain/Context/Rules.

- **Коллекция без выбора и без имени в UI**: ни название, ни тип контейнера,
  ни ручная привязка коллекции на этом шаге не показываются (`.plan`: «скрыв
  название/тип контейнера и ручную привязку») — пользователь видит только
  список источников и способ добавить новый. Личная коллекция агента
  (`resources.collectionId`) заводится лениво самим `wizardStore.ensureCollection`
  при добавлении первого источника, не при входе на шаг; имя коллекции —
  `getWizardKnowledgeCollectionName(fields)` (текущее `fields.agentName`, с
  fallback-подписью, если оно ещё пусто).
- **Статусы источника**: `loading` (источник ещё не стал fixture-объектом —
  чисто клиентское состояние без стабильного id, не часть draft'а: ничего не
  создаётся, если уйти со страницы раньше) → `processing`
  (`KnowledgeObject.status === "indexing"`) → `ready`/`error`
  (`indexed`/`error`, тот же таймер-конвенция, что `components/knowledge/Files.vue`
  — каждый третий источник демонстративно уходит в ошибку). Ошибка даёт
  «Повторить» (детерминированно завершается успехом — ретрай не должен
  запирать демо в бесконечной ошибке), у любого сохранённого источника есть
  «Заменить» (удаляет и переоткрывает форму текста/ссылки с прежним именем;
  для файла просто освобождает место в уже видимой зоне загрузки) и удаление
  — все три не трогают остальные источники и другие коллекции/агентов
  (`wizardStore.removeKnowledgeSource` работает только в пределах текущего
  draft'а и его коллекции).
- **Продолжение без источника разрешено**: шаг не входит в
  `isStepComplete`'s switch — по умолчанию он всегда считается пройденным
  (тот же диспетчер, что в Task A9.3), поэтому «Далее» не блокируется
  отсутствием знаний.
- **Синхронизация имени**: коллекция помечена `autoNamed` (`stores/knowledge.js`)
  только когда её создал `wizardStore.ensureCollection`. Пока флаг не сброшен,
  `knowledgeStore.syncAutoName` держит имя коллекции равным текущему
  `fields.agentName` при каждом его изменении (возврат на «Контекст» и
  редактирование имени там). Явный `updateCollection` — единственный путь
  обычного экрана настроек коллекции (`components/knowledge/Settings.vue`) —
  сбрасывает `autoNamed` в `false`, и дальнейшая автоподстановка по имени
  агента останавливается независимо от того, продолжается ли ещё сам мастер.
  Смена locale имя не трогает: синхронизация реагирует только на
  `fields.agentName`, никакой locale-производной строки в этом расчёте нет.

### Мастер создания агента: шаг «Песочница» (Task A9.6)

`SandboxStep.vue` — тест агента "от лица клиента" перед запуском: сценарный
пример вопроса (когда у выбранного в шаге «Боль» сценария он есть — у «Другая
задача» нет), два общих вопроса, явный «вопрос без ответа» и своя строка
ввода. Транскрипт — чисто локальное состояние компонента: он никогда не
пишет в `useAgentsStore()`'s `messages`/`sendMessage` и не создаёт канал
(`useChannelsStore()` в компоненте не используется вовсе) — сообщения не
публикуются клиентам буквально, не только по формулировке подсказки.

- **Ответ — размеченный демо-шаблон, не результат реального ИИ**
  (acceptance): `WIZARD_SANDBOX_ANSWERED_REPLY` (`stores/wizard.js`) прямо
  называет себя демонстрацией, а не сгенерированным ответом. Вопрос считается
  «отвечаемым» (`hasAnswer: true` — сценарный/общий/свой) только пока в
  личной коллекции draft'а есть хотя бы один `indexed`-источник; иначе, и
  всегда для явного «вопроса без ответа», ответ — одна из
  `WIZARD_SANDBOX_NO_ANSWER_REPLIES`, подобранная по текущему
  `fields.noAnswerAction` (Task A9.3) — песочница показывает именно то
  поведение, которое выбрано на «Правилах», а не общую заглушку.
- **Pending не выглядит success**: реплика агента появляется с небольшой
  задержкой (`setTimeout`) — сообщение оператора и ответ агента визуально
  различимы («Проверено» фиксируется только по факту показанного ответа, не
  в момент отправки вопроса). Подпись проверяемой конфигурации
  (`getSandboxVerificationSignature`) фиксируется в момент отправки вопроса,
  а не срабатывания таймера: если пользователь успевает за эти 400мс уйти на
  «Изменить правила»/«Изменить знания» и поменять там что-то, `markSandboxVerified`
  по срабатыванию таймера сверяет текущую подпись с зафиксированной и не
  помечает изменённую (никогда не протестированную) конфигурацию как
  проверенную (post-review fix, Task A9.6).
- **S2 "изменения не проверены"** (`.plan` шаг 5): `wizardStore.markSandboxVerified`
  сохраняет не факт/время, а подпись всего, от чего зависит ответ —
  `getSandboxVerificationSignature(draft)` (задача/стиль/ограничения/реакция
  на отсутствие ответа/условие связи с оператором/класс модели/набор ключей
  источников знаний). `isSandboxVerificationStale(draft)` сравнивает эту
  подпись с текущей: `false`, пока проверки вообще не было (отдельное
  состояние «ещё не тестировали», не «устарело»), `true` — как только любое
  из перечисленных полей поменялось после последней проверки. Шаг показывает
  `b-message type="is-warning"` вместо тихого «зелёного» статуса и
  предлагает отправить новый вопрос, а не автоматически перепроверяет
  что-либо сам. «Изменить правила»/«Изменить знания» — прямой переход
  (`AgentWizard.vue`'s `goToStepDirect`, минуя проверку `canAdvance`, которая
  относится только к движению «Далее») на соответствующий шаг, откуда можно
  вернуться назад в «Песочницу» тем же способом, что и на любой другой шаг.

### Система статусов агента: S2 (Task A9.6)

Кит реализует рекомендованный `.plan`'ом вариант **S2** — «жизненный цикл +
состояние подключения» — как производную presentation-модель поверх
существующих fixture-полей, а не новый серверный контракт: `Agent.status`
(`AGENT_STATUSES` — `Активен`/`Черновик`/`Приостановлен`, `stores/agents.js`)
и `Channel.status` (`ChannelRuntimeStatus`, `stores/channels.js`) остаются
как есть, ни один enum не переименован и не выдан за согласованный с API.

**Lifecycle агента** (`getAgentLifecycle`/`getAgentStatusProjection`,
`stores/agents.js`) — четыре presentation-состояния, только два из которых
совпадают со значением `Agent.status` буквально:

| Lifecycle | Источник | Когда |
|---|---|---|
| `draft` | `status === "Черновик"` | `isAgentReadyToLaunch(agent)` (fixture-прокси: непустая `instructions`) — `false` |
| `ready` | `status === "Черновик"` | `isAgentReadyToLaunch(agent)` — `true`; тот же серверный статус, что `draft`, но задача/правила уже заданы и запуск ещё не выполнен |
| `active` | `status === "Активен"` | — |
| `paused` | `status === "Приостановлен"` | — |

**Per-channel connection state** (`getChannelConnectionState`,
`stores/channels.js`) — те же четыре значения, что называет `.plan`:

| Connection state | `Channel.status` |
|---|---|
| `connected` | `active` |
| `error` | `error`, `displaced` |
| `not_connected` | `inactive`, `paused` |
| `checking` | производится шагом «Telegram» (Task A9.7 T2, `startChannelCheck`) на время между отправкой токена и явным подтверждением/ошибкой |

**Карточная проекция** (`getAgentStatusProjection`, потребляется
`Agents.vue`): `draft`/`ready`/`paused` показывают только свою lifecycle-
подпись, каналы не проверяются — «Готов к запуску» не значит «уже отвечает»
(`.plan`: не смешивать эти два состояния). Для `active`:

- нет ни одного `connected`-канала (включая случай отсутствия каналов вовсе
  не проверяется — пусто ≠ ошибка, а вот "все каналы `not_connected`/`error`"
  считается) → основная подпись **«Не отвечает: ошибка подключения»**
  (`is-danger`), `attentionMessage` — причина первого проблемного канала;
- есть хотя бы один `connected`, но другие в `error` → подпись остаётся
  «Активен», а отдельная строка на карточке называет конкретный канал —
  сбой одного канала не переименовывает и не скрывает статус остальных
  (`.plan`: «Наличие ошибки одного канала не скрывает работу остальных»);
- все каналы `connected` (или каналов ещё нет) → «Активен» без
  предупреждения.

`needsAttention`/`badgeType` не единственный носитель смысла — `Agents.vue`
всегда рендерит и текстовую подпись (`badgeLabel`), и, при
`needsAttention`, отдельную текстовую строку (`attentionMessage`): статус не
кодируется только цветом (`.plan`).

### Dashboard: «Требует внимания» и метрики (Task A10.4)

`Dashboard.vue` собирает S2-причины со всего непустого обзора вместо
единственной агентской карточки — пять источников, каждый чистая
производная уже существующего fixture-состояния соответствующего стора, не
второй источник истины и не новый серверный контракт:

| Причина | Источник | Действие карточки |
|---|---|---|
| Настройка не завершена | `wizardStore.getDraft(workspaceId)?.status === "in_progress"` | `agent-wizard` (тот же общий вход — `ensureDraft` сам резолвит шаг) |
| Знания не готовы | `getCollectionAttentionReason` (`stores/knowledge.js`): объект коллекции в `"error"` либо последний прогон переиндексации `"error"` | `knowledge-collection` |
| Канал недоступен | `getChannelsNeedingAttention` (`stores/channels.js`, тот же helper, что карточка агента) по каждому агенту пространства | `agent-channels` |
| Диалог передан оператору | `needsOperatorAttention`/`Conversation.awaitingOperator` (`stores/conversations.js`) — тот же presentation-only флаг Task A10.4, теперь дополненный owner/lease-моделью Task A10.5 (см. «Диалоги: очередь, handoff owner/lease и delivery states» ниже); карточка не различает «уже забрал оператор» и «ещё в очереди» — оба случая остаются `awaitingOperator: true` | `conversation` |
| Лимит почти исчерпан/исчерпан | `getLimitsNeedingAttention` (`stores/workspace.js`): лимит в состоянии `"exhausted"`, либо измеренный (`state: "ok"`) у порога `threshold` (по умолчанию 90) — заголовок карточки берёт формулировку из `limit.state` («…исчерпан» для `"exhausted"`, «…почти исчерпан» только для near-threshold `"ok"`, чтобы не противоречить `limit.caption` рядом), см. «Семиключевой контракт ресурсов и лимитов» ниже для полного состояния `state`/`progress` | `workspace-plans` |

Ошибка одного канала добавляет отдельную карточку и не подменяет и не
скрывает статус работающего агента/остальных карточек рядом (`.plan`:
«Наличие ошибки одного канала не скрывает работу остальных») — раздел просто
не рендерится, когда причин нет, вместо пустой карточки-заглушки.

**Пустой dashboard** (`agents.length === 0`, либо demo-режим `empty`)
остаётся входом Task A9.2: CTA-карточка всегда ведёт в `agent-wizard`
(его собственный `ensureDraft` прозрачно продолжает существующий черновик),
подпись/подзаголовок лишь заранее называют это «Продолжить настройку
агента», когда `wizardStore.getDraft(workspaceId)` уже существует и
`in_progress` — второго мастера или отдельного онбординга нет.

**Метрики** (диалоги за сегодня, доля доставленных исходящих сообщений,
измеренные лимиты тарифа) показывают время снятия снимка (`Обновлено:
HH:MM`) рядом с заголовком секции. Доля доставки — реальная величина
(`delivered`/`read` от общего числа исходящих сообщений с `delivery`), явно
про доставку, а не про качество ответа (`.plan`: «техническую доставку не
называть качеством помощи»); при нуле исходящих сообщений показывает «—» и
подпись «Нет отправленных сообщений», а не сфабрикованные «0%» — unknown не
подменяется нулём. Число диалогов за сегодня — настоящий подсчёт (может быть
честным нулём). Прежние фиктивные `dashboards`/`emptyDashboard` (выдуманные
дельты, «из 500 GB» без привязки к тарифу, «Успешные ответы» без измеримой
семантики) удалены — плитки быстрой навигации и таблицы «Последние
агенты»/«Последние диалоги» читают те же реальные fixture-хранилища.

### Семиключевой контракт ресурсов и лимитов (Task A10.6)

`stores/workspace.js` — единственный источник тарифных лимитов, читаемый
`Dashboard.vue`, `common/TariffSummaryCard.vue` (сайдбар) и
`workspace/Usage.vue` («Обзор пространства»); `WorkspacePlans.vue` через
`TariffSelector` показывает тот же набор ключей как каталог планов, без
`used` (см. ниже). Источник — реальный контракт `/workspaces/{id}/usage`
(API Issue #106), не вымышленные `credits`/`monthly_budget`/прогноз стоимости.

- **Семь ключей, `RESOURCE_LIMIT_KEYS`:** `workspace_members`, `agents`,
  `knowledge_collections`, `knowledge_objects`, `channels`,
  `knowledge_extracted_bytes` (байты, период `monthly`),
  `active_conversations_monthly` (счётчик, период `monthly`) — остальные пять
  без периода (совокупный счётчик, не сбрасывается помесячно). Предыдущий
  fixture-ключ `credits` убран целиком, не переименован: платформа не
  предоставляет ни расход в валюте, ни курс кредитов, а придумывать его
  значило бы нарушать «UI не обещает стоимость/прогноз без данных».
- **`createLimit(key, { used, limit, state })`** — единственное место, где
  `{ used, limit }` (или явный `state: "unknown" | "error"`) превращается в
  готовый `{ label, caption, progress, state }`; ни один экран не форматирует
  подпись лимита самостоятельно. `state` — один из `"ok"`, `"zero"`
  (`limit === 0`, ресурс не входит в тариф), `"unlimited"` (`limit === null`),
  `"unknown"` (значение ещё не посчитано), `"exhausted"` (`used >= limit`),
  `"error"` (временная ошибка получения именно этого ресурса, независимая от
  глобального demo-режима `stores/demo.js`). `progress` — число 0-100 только
  для `"ok"`/`"exhausted"`; для остальных состояний — `null`, поэтому ни один
  экран не рисует полосу или «0%» для `unlimited`/`unknown`/`error`/`zero` —
  различие видно только текстом caption'а (`getLimitsNeedingAttention` в
  `Dashboard.vue` тоже смотрит на `state`, не на `progress`).
- **Фикстуры трёх воркспейсов вместе покрывают все шесть состояний:**
  `demo` — `ok` (участники/агенты/коллекции/диалоги), `exhausted`
  (`knowledge_objects`, 200 из 200), `zero` (`channels`, Free без каналов),
  `unknown` (`knowledge_extracted_bytes` — метрика ещё не посчитана);
  `trickster` — `unlimited` (агенты/коллекции/диалоги на Superior);
  `empty` — `error` (`channels`) наравне с честными `ok`-нулями (`used: 0`
  при реальном `limit`, что не то же самое, что `zero`-состояние).
- **`formatResourceCapCaption(key, cap)`/`getResourceLimitLabel(key)`** —
  экспортированы из `stores/workspace.js` для `WorkspacePlans.vue`: тот же
  словарь подписей/единиц/периода, что `createLimit`, но без `used` — план
  описывает возможность тарифа (`cap`), не измеренный расход конкретного
  воркспейса. Значение `cap === 0` читается как «Не входит в тариф» (то же
  текстовое правило, что `zero` у `createLimit`), `cap === null` — «Без
  ограничений».
- Байты форматируются тем же округлением, что уже использует
  `knowledge/Statistics.vue`/`knowledge/Files.vue`'s локальный `formatBytes`
  (Б/КБ/МБ/ГБ, не общий модуль — тот же паттерн, что и там).

### Диалоги: очередь, handoff owner/lease и delivery states (Task A10.5)

Расширяет Task A5.7/A8.4's список/деталь диалога и Task A10.4's S2-флаг
`awaitingOperator` собственной owner/lease-моделью — всё ещё fixture-only,
без серверных claims, без реального таймера (`stores/conversations.js` не
использует `setInterval` нигде, поэтому `leaseExpired` — плоский fixture-флаг
на объекте диалога, а не `expiresAt`, сравниваемый с `Date.now()`). Форма
мирит get.3xtr.im's `chat.status === "escalated"` + `chat.operator_lease`
контракт (`modules/conversations/views/Conversation.vue`'s `iOwnLease`/
`canInterfere`/`canReturnControl`) с уже существующими полями кита, не
переименовывая `Conversation.status` (диалоговый «Активен»/«Завершён», не
эскалация):

- `Conversation.awaitingOperator` остаётся единственным флагом эскалации
  («очередь») — не выводится ни из `updated`, ни из времени последнего
  сообщения.
- `Conversation.handoff: { owner: { id, name } | null, leaseExpired: boolean }`
  — `owner` задан, пока диалог кто-то ведёт (сохраняется даже при
  `leaseExpired: true`, чтобы показать «был(а) …»); `leaseExpired: true`
  означает, что владение устарело и диалог может забрать любой оператор,
  включая прежнего владельца (`ownsHandoff` намеренно возвращает `false` для
  него в этом состоянии).
- Текущий оператор — `profileStore.profile` (`id`/`name`, Task A10.5 добавил
  `id`, см. `stores/profile.js`'s собственный комментарий к полю) — тот же
  «Иван Петров»/id 1, что уже используют `members.js` (владелец `demo`) и
  `administration.js`.

Пара чистых предикатов в `stores/conversations.js` — единственный источник
истины для UI и стора: `ownsHandoff(conversation, operatorId)` (активный
lease именно у этого оператора) и `isHandoffClaimable(conversation)`
(диалог эскалирован и либо не занят, либо lease истёк).

**Команды.** «Взять диалог» (`claimHandoff`) и «Вернуть агенту»
(`releaseHandoff`) — отдельные fixture-команды в `stores/conversations.js`,
не связанные ни с сохранением формы, ни друг с другом:

- `claimHandoff` — no-op success, если оператор уже владеет; конфликт
  (`ok: false, reason: "owned-by-another"`) при активном чужом lease;
  claim истёкшего lease — успех без конфликта; успешный claim также
  выставляет `awaitingOperator: true` (мирит get.3xtr.im's `interfere()`,
  эскалирующий и забирающий lease одним вызовом).
- `releaseHandoff` — только текущий активный владелец может освободить;
  снимает эскалацию целиком (`awaitingOperator: false`, `owner: null`) — это
  не «вернуть в очередь», а «диалог больше не нуждается в операторе»,
  мирит `returnControl()`.
- Оба возвращают `{ ok, reason?, handoff? }` — `handoff` присутствует и при
  конфликте, так что вызывающей стороне не нужен отдельный «рефетч»: стор
  синхронный, актуальное состояние уже в возвращённом объекте.

**Конфликт при отправке.** `sendMessage(workspaceId, conversationId, text,
operator)` теперь гейтится тем же `ownsHandoff` на эскалированном диалоге:
оператор без активного lease получает `{ ok: false, reason }`
(`"owned-by-another"` при активном чужом владении, `"lease-missing"` для
незанятого/просроченного) вместо отправки. `conversations/History.vue`
(композер) не очищает черновик при `ok: false` — набранный текст остаётся в
поле, предупреждение над композером называет текущего владельца из
`result.handoff` (той же реактивной записи стора, что уже показывает тег
владельца в `ConversationHeader.vue` — «обновлять» отдельно нечего,
состояние уже актуально). Владелец активного lease отправляет как в обычном
(не эскалированном) диалоге — сигнатура и поведение `sendMessage` для
неэскалированных диалогов не изменились.

**Owner/lease в интерфейсе** (`conversations/ConversationHeader.vue`): пока
`awaitingOperator` истинен, рядом с тегами канала/статуса — тег владельца
(«Требует оператора» / «Отвечает: …» / «Ведёте вы» / «Владение истекло —
был(а) …») и кнопка «Взять диалог» (когда `isHandoffClaimable` и это не
текущий владелец) либо «Вернуть агенту» (когда `ownsHandoff`) — никогда обе
сразу. Конфликт claim/release практически недостижим через саму демо-UI
(в ките нет второго актора, чтобы гонка была реальной) — соответствующие
ветки стора покрыты unit-тестами напрямую;
реально достижимый через UI конфликт — именно отправка сообщения в чужой
эскалированный диалог, см. выше.

**Delivery states.** `queued`/`sending`/`delivered`/`read`/`failed`/
`cancelled` (`MessageDelivery.status`, Task A5.7) остаются как есть —
Task A10.5 добавил фикстуры `queued`/`cancelled` (ранее не встречались ни в
одном диалоге демо-пространства) и ужесточил `retryMessageDelivery`:
повтор меняет статус только для сообщения, у которого `status === "failed"
&& retryable === true` — тот же guard, что уже стоит на кнопке «Повторить»
в `MessageDeliveryStatus.vue`, теперь и в самом сторе, так что прямой вызов
не может обойти его.

**Fixture-каталог `demo`** (`stores/conversations.js`): диалог 1 —
эскалирован, не занят (очередь); 5 — эскалирован, активный чужой lease
(конфликт при отправке); 6 — эскалирован, владеет текущий оператор
(«Вернуть агенту», отправка разрешена); 7 — эскалирован, lease истёк
(claim без конфликта). Остальные диалоги фикстуры не эскалированы и несут
явный `handoff: { owner: null, leaseExpired: false }` по умолчанию.

### Мастер создания агента: шаг «Telegram», T1/T2 (Task A9.7)

`TelegramStep.vue` — два способа подключения бота рядом
(`.tr-wizard-telegram-methods`), ни один не переводит канал в `active`: это
остаётся явным действием Task A9.8 («Включить ответы в Telegram»). Соответствует
`.plan` шагу 6 «Telegram и вариант QR».

- **T1 «Способ 1» — демо-макет, не интеграция.** На 2026-09-12 официальный
  протокол привязки Telegram-пользователя/результата создания managed-бота к
  конкретному draft'у (owner/correlation) не согласован (внешние API Issues
  #114–#118) — QR (десктоп, `.tr-wizard-telegram-qr`) и «Открыть Telegram»
  (мобильный, `.tr-wizard-telegram-open-mobile`, оба класса переключаются тем
  же 768px-брейкпоинтом, что и остальной "14. Responsive") показаны только как
  геометрический макет: QR не кодирует ссылку и не содержит секрет, кнопка
  `disabled`, ни один клик не переводит канал в подключённое состояние.
  Явный `b-tag` «Демо-макет» и текст «Способ недоступен — используйте вариант
  ниже» держат T2 всегда предложенным рядом (acceptance: «Недоступный T1
  всегда предлагает T2»). Перечень описанных (не интерактивных) состояний —
  ожидание действия в Telegram, отмена/возврат без результата, истёкшая
  сессия привязки — держит `.plan`'ов список UI-состояний видимым без
  обещания рабочей интеграции.
- **T2 «Способ 2» — единственный рабочий путь**, официальный fallback через
  `@BotFather`: «Создать нового бота» / «Подключить существующего» отличаются
  только контекстным текстом шагов, оба ведут к одному полю токена
  (`b-input type="password"`, ни разу не логируется и не попадает в URL/QR).
  `classifyTelegramToken` (`stores/wizard.js`) — детерминированная
  fixture-классификация без сети (подстроки `invalid`/`taken`/`conflict`, тот
  же приём, что «каждый третий источник знаний» в `KnowledgeStep.vue`):
  неверный токен и конфликт подключения показывают разный текст ошибки
  (`b-message type="is-danger"`) с «Попробовать снова»/«Назад», ни один не
  выдаёт себя за успех.
- **Проверка и подтверждение — два разных клика.** Успешная классификация не
  подключает канал сама по себе: она переводит его в промежуточный
  `"checking"` (см. ниже) и показывает найденное `@username` в
  `b-notification`, требуя отдельного «Подтвердить подключение» — только этот
  клик вызывает `channelsStore.confirmChannelIdentity`, которая возвращает
  канал в `"inactive"` с заполненным `providerIdentity`/`providerPublicUrl`, не
  в `"active"` (acceptance: «QR/deep-link и token не приводят к активному
  статусу без fixture-подтверждения»). «Ввести другой токен»/«Подключить
  другой аккаунт» откатывают через `resetChannelStatus`, не трогая уже
  подтверждённую identity предыдущей попытки, пока новая ещё не подтверждена.
- **Fixture-ресурсы создаются лениво и идемпотентно.** Токен впервые
  отправлен → `wizardStore.ensureTelegramChannel` заводит агента (если
  `resources.agentId` ещё пуст — `getWizardAgentName` откатывается на «Новый
  агент» при прямом URL мимо «Контекста») и Telegram-канал, запоминая
  `resources.channelId`; повторная отправка формы того же draft'а находит уже
  созданный канал вместо второго — та же схема, что `ensureAgent`/
  `ensureCollection` (Task A9.1/A9.4).
- **«Подключить позже»** не удаляет draft ни уже созданные им ресурсы — прямой
  переход на «Проверка и запуск» тем же `go-to-step`, которым «Песочница»
  переходит на «Правила»/«Знания» (Task A9.6).
- **Уход с экрана подтверждения не оставляет канал зависшим в `"checking"`**
  (post-review fix): «Подключить позже», «Назад»/«Отменить» из
  `AgentWizard.vue` и любой другой уход со шага, пока найденная личность бота
  ещё не подтверждена, размонтируют `TelegramStep.vue`, не вызывая ни
  `confirmConnection`, ни `backToChoose`. `onBeforeUnmount` этого компонента
  откатывает такой канал в `"inactive"` тем же `resetChannelStatus`, что и
  явный откат — обычный экран каналов почти никогда не встречает `"checking"`
  снаружи мастера. Если всё же встречает — `ChannelCard.vue` показывает лейбл
  «Проверяется» вместо сырого статуса, а «Изменить» (уже доступное для любого
  нефейлящего канала) реально разрешает его: `updateChannel` с переданным
  токеном сбрасывает `"checking"` в `"inactive"` тем же путём, что и `"error"`.
  Таймер `submitToken`'s паузы (500мс) сохраняется в переменной и явно
  отменяется в этом же `onBeforeUnmount`, причём первым делом, до отката
  статуса канала (post-review fix): без `clearTimeout` отложенный callback
  всё равно срабатывал бы после ухода и заново записывал invalid/conflict-токен
  в `"error"` поверх только что восстановленного `"inactive"` — отменённая
  или покинутая попытка подключения переживала бы отмену пользователя.
- **S2 `"checking"`** (`ChannelRuntimeStatus`/`getChannelConnectionState`,
  `stores/channels.js`) реализован этой задачей — ранее зарезервированное в
  таблице S2 (Task A9.6) значение, которое фикстуры не производили: теперь
  канал держит его на всё время между отправкой токена и явным подтверждением
  (или ошибкой), не раньше и не позже.

### Мастер создания агента: шаг «Проверка и запуск» (Task A9.8)

`ReviewStep.vue` — финальный шаг мастера, соответствующий `.plan` шагу 7:
аудит собранной конфигурации и два раздельных явных действия, ни одно из
которых не совпадает с обычной кнопкой шапки «Сохранить черновик» (та просто
уходит из мастера, не трогая агента — см. Task A9.1/A9.2). Это единственный
шаг, который реально записывает `fields` на агента и единственное место,
включающее ответы (`.plan`: «Активация: review → подтверждённый успех →
активное состояние»). После `completeDraft` (сохранение без запуска либо
успешный запуск) `AgentWizard.vue` скрывает «Назад»/«Отменить»/«Сохранить
черновик»/«Далее» (post-review fix) — review → confirmed success
терминально: с него нельзя молча вернуться в Telegram/Rules уже после того,
как агент запущен или draft сохранён, доступны только post-launch действия
самого `ReviewStep.vue` ниже.

- **Аудит** (`.tr-wizard-review-summary`, plain `<dl>`): имя агента, аудитория/
  задача (`scenario`/`fields.task`), сводка знаний (кол-во источников и их
  статусов — готово/обрабатывается/ошибка, из `useKnowledgeStore()`), правила
  (стиль/реакция на отсутствие ответа/условие связи с оператором/
  ограничения), класс модели (те же локализованные подписи
  `t.modelClass[classId].label`, что и «Правила», Task A9.5), состояние
  Telegram-канала и его лимиты (`Channel.limits`), и текстовое объяснение
  последствий запуска. Каждая строка — факт, не элемент выбора; изменить
  что-либо отсюда нельзя — только вернуться на нужный шаг (`go-to-step`,
  ссылка «Подключить сейчас» у неподключённого Telegram).
- **`wizardStore.finalizeAgentFields`** — общая для обоих действий запись: не-
  BYOK модель (точный выбор каталога из экспертной зоны либо рекомендованная
  модель выбранного класса), температура, финальная инструкция
  (`resolveWizardInstructions` — та же ветка `custom`/`template`, что превью
  `ExpertParameters.vue`) и BYOK-состояние. Идемпотентна по агенту
  (`ensureAgent`) и по повторному вызову; невалидный BYOK-патч (переключён, но
  без ключа/модели) отклоняется тем же `isByokSaveValid`-рубежом, что и
  `AgentSettings.vue` — отдельной копии проверки здесь нет.
- **«Сохранить без запуска»** (`wizardStore.saveDraftWithoutLaunch`) —
  применяет `finalizeAgentFields` и завершает draft (`completeDraft`), ни разу
  не трогая канал: агент остаётся в lifecycle `draft`/`ready` (`stores/
  agents.js`), «Готов к запуску» без единого включённого ответа (acceptance
  S2: «Сохранение draft не включает ответы»).
- **«Включить ответы в Telegram»** (`wizardStore.launchAgent`) требует уже
  подтверждённый на шаге «Telegram» канал (`channel.providerIdentity`
  заполнен) — без него кнопка `disabled` и explicit `reason: "no_channel"`
  вместо того, чтобы создавать канал по догадке. При успехе: `finalizeAgentFields`
  → `channelsStore.activateChannel` → прямое `agent.status = "Активен"` внутри
  этой же атомарной цепочки launch (не через отдельный `setAgentStatus` —
  Stage A10 review fix ввёл его как явную lifecycle-команду с confirm для
  `AgentSettings.vue`, но launch не запрашивает подтверждение на каждый свой
  внутренний шаг) → `completeDraft`. Retry-safe: повторный вызов не
  создаёт второго агента/канала (`ensureAgent`/`activateChannel` сами
  идемпотентны) — acceptance «retry не дублирует channel».
- **Пост-launch действия** показываются по завершении draft'а и включённому
  каналу (`channel.isEnabled`, а не по живому `agent.status` — иначе
  последующая пауза откатила бы экран обратно к черновик-виду): «Открыть
  бота» (внешняя ссылка `channel.providerPublicUrl`, тот же `<a class="button">`
  приём, что `ChannelCard.vue`), «Перейти к диалогам»
  (`{ name: "conversations-agent", params: { agentId } }`), «Приостановить/
  Возобновить ответы» (прямой toggle `agent.status` — «Приостановлен»
  переименовывает именно пользовательскую остановку, не ошибку канала,
  `.plan`: «ошибка канала сама по себе не переименовывается в пользовательскую
  паузу») и «Создать следующего агента» (`wizardStore.startDraft` + переход на
  `pain` — новый draft, не продолжение текущего; основной путь без экспертного
  личного сценария).
- **«Сохранить без запуска» тоже показывает пост-действие**: если draft
  завершён, но канал не включён, шаг показывает отдельную панель «Черновик
  сохранён» со ссылкой на настройки агента и тем же «Создать следующего
  агента» — не показывает несуществующий успех запуска.

### Мастер создания агента: contract и границы downstream (Task A9.9)

Задачи A9.1–A9.8 реализовали мастер по частям; этот раздел фиксирует итог как
**kit specification** — цельное описание того, что мастер уже делает как
backend-less UI-контракт, и того, что явно остаётся отдельным product/API-
решением. Источник — `.plan` Stage A9 («Риски», «Критерии приёмки») и матрица
API-issues в конце `.plan`; исходный `docs/ux-review-2026-09-11.md` этим
разделом не заменяется и не редактируется.

**Что мастер реализует как готовый kit-контракт** (не требует API, чтобы быть
проверяемым здесь):

- Один route-driven controller (`AgentWizard.vue`) и одна модель состояния
  (`useWizardStore`) на все семь смысловых шагов, все точки входа, direct
  URL/back-forward/невалидный шаг и переключение пространства — разделы
  «Точки входа», «Боль/Контекст/Правила» выше.
- Связка агент↔коллекция по стабильным ID (не по имени), идемпотентные
  `ensureAgent`/`ensureCollection`/`ensureTelegramChannel` — повтор шага или
  submit не создаёт вторую сущность (разделы «Знания», «Telegram», «Проверка
  и запуск»).
- Presentation-проекция S2 (`getAgentLifecycle`/`getAgentStatusProjection`/
  `getChannelConnectionState`) поверх существующих enum'ов `Agent.status`/
  `Channel.status` — ничего не переименовано на уровне fixture-данных.
- Fixture-профили тарифов/классов моделей (`WIZARD_CAPABILITY_PROFILES`,
  `MODEL_CLASSES`) как иллюстрация трёх сценариев (младший/расширенный/
  единственный класс), не как согласованная тарифная матрица продукта.
- T1 (QR/deep-link) как визуальный макет без сети и без секрета в коде, T2
  (BotFather + токен) как единственный интерактивный fixture-путь с
  детерминированной классификацией токена и явным подтверждением identity.
- Полный одинаковый набор RU/EN/ES ключей нового пути (`src/locales/wizard/**`,
  `tests/unit/locales/wizard.test.js`) — scoped к мастеру и экспертной зоне,
  не кит-wide i18n (см. «Locale экспертной зоны» выше).
- In-memory persistence на время сессии: `useWizardStore` живёт в Pinia

и вкладки `NavbarTabs` для этого нет — у диалога нет собственного меню в
навбаре, только общая шапка со стрелкой назад слева. Структура повторяет
`conversations/views/Conversation.vue` из get.3xtr.im (список + чат +
properties-aside), только без роутинга настроек — там `/settings` остаётся
собственным маршрутом (см. `docs/agent-migration-guide.md`, раздел 6).

### Меню страницы в Navbar

**Контракт (реализовано в Task A4.3).** Оболочка (`App.vue`) предоставляет
DOM-target через provide/inject (`navbarMenuKey` из
`src/composables/navbarMenu.js`) и размещает его в слоте `menu` компонента
`Navbar.vue` (`<div ref="navbarMenuTarget" class="tr-topbar__menu" />`); а
страница из вложенного `RouterView` (например, `Workspace.vue` для ветки
`/workspace`) выводит туда свои вкладки через компонент `NavbarMenu`
(Teleport-обёртку, `src/components/common/NavbarMenu.vue`):

```vue
<NavbarMenu>
  <NavbarTabs :items="tabs" :aria-label="…" />
</NavbarMenu>
```

Правила контракта:

- `NavbarMenu` использует Teleport: обработчики, permissions и реактивное
  состояние остаются у страницы. До появления target (пока App.vue не
  смонтировал `navbarMenuTarget`) меню не рендерится, оно удаляется при
  unmount, скрывается при `KeepAlive` deactivation (`onDeactivated`) и
  восстанавливается при activation (`onActivated`).
- На одну ветку маршрутов назначается один владелец меню — обычно родитель
  раздела (`Workspace.vue` для всех `/workspace/*`). Вложенные страницы
  используют его либо рендерят собственное меню вместо родительского.
  Несколько одновременно смонтированных `NavbarMenu` добавляют содержимое в
  один target — Teleport конфликтов не создаёт.
- Target не создаёт собственного layout-блока, в том числе когда он пуст:
  `.tr-topbar > .tr-topbar__menu { display: contents; }` в
  `trickster-buefy.scss` — пустой target не добавляет flex-item и не
  оставляет зазор в `.tr-topbar`, а телепортированный `NavbarTabs` становится
  прямым flex-item `.tr-topbar`, как и при прежнем прямом рендеринге.
- Ниже `1024px` вкладки прокручиваются горизонтально в одной строке навбара
  — поведение не изменилось.
- Жёсткой route-проверки (бывший `isWorkspaceRoute` в `Navbar.vue`) больше
  нет: `Navbar.vue` ничего не знает о конкретных разделах, он лишь
  предоставляет слот `menu`.

Ограничение кит-версии по сравнению с целевым `get.3xtr.im`-контрактом:
кит-экраны — статичные демо без реальной загрузки (см. «Что этот репозиторий
представляет собой»), поэтому правило «меню появляется после загрузки данных
раздела; при loading и error его нет» здесь не применяется — `Workspace.vue`
рендерит `NavbarMenu` безусловно. Это фиксируется как факт кит-реализации, не
как расхождение, которое нужно чинить: воспроизвести loading/error-gating
верно можно только вместе с `AsyncState`/`ListAsyncState` (план Stage A4,
Task A4.4).

`items` компонента `NavbarTabs.vue` в ките — `{ label, to }`; поддержки
`icon` (иконка вместо подписи) в его коде нет, хотя классы
`.tr-navbar-tabs__icon` и `.tr-navbar-tabs__link--icon` присутствуют в
`trickster-buefy.scss` — это перенесённые из прежнего `ToolbarTabs`
`@deprecated`-алиасы для `get.3xtr.im` (Task A3.3, до Stage B4), а не
подключённая функциональность `NavbarTabs.vue`.

> **Именование.** Компонент называется `NavbarTabs`, потому что это вкладки
> навбара, а не toolbar страницы. Прежнее имя `ToolbarTabs` и класс
> `.tr-toolbar-tabs` пересекались с `tr-page-toolbar` — другой, независимой
> сущностью. Переименовано в Task A3.3; `.tr-toolbar-tabs*` остаётся
> `@deprecated`-алиасом до Stage B4 (см. `agent-migration-guide.md`,
> «Реестр алиасов миграции»).

из единого `UiKit.vue` в `components/kit/NavigationStates.vue` при
разделении `/kit` на маршрутные подразделы, Task A8.6).**
`kit/NavigationStates.vue` собирает
контракты Task A7.3–A7.5 в одном обозримом месте — не подборку ручных
несвязанных примеров, а витрину всех шести значений `DEMO_MODES`, каждое из
которых показано тем же реальным компонентом, который его рендерит на
маршрутах кита. **Это не таблица «контракт × все шесть режимов» — ни один
раздел не показывает все шесть карточек сразу**, потому что сами контракты
неравнозначны: `ListAsyncState` структурно не имеет ветки `permission-denied`
(на маршрутах она всегда рендерится отдельным прямым `AsyncState`, а не через
`ListAsyncState`), а прямой `AsyncState` не имеет варианта `empty`/`partial`
(тем более что `partial` — вообще не вариант `AsyncState`, а баннер поверх
контента). Соответственно: раздел «Каталог/список — ListAsyncState»
перебирает `ready`/`loading`/`empty`/`error` через сам `ListAsyncState`,
раздел «Detail/сводный экран — прямой AsyncState» — `ready`/`loading`/`error`
плюс `permission-denied` через прямой `AsyncState` (без отдельной карточки
`empty` — она уже показана в разделе «Каталог/список», и без
`permission-denied` в первом разделе — там, где он реально нужен на
маршрутах, он тоже показывается прямым `AsyncState`, а не `ListAsyncState`),
раздел «Partial» — тот же `b-message type="is-warning"`-баннер поверх ещё
доступного контента, что в `Agents.vue`/`Files.vue`. Карточки матрицы читают
только статичные тексты `useDemoStore().listAsyncState` /
`permissionDeniedState` (read-only проекция стора, без дублирования строк) и
не подписаны на его текущий `mode` — карточки в пределах каждого раздела
рендерятся одновременно, независимо от того, что выбрано в демо-панели
навбара, поэтому открытие этого раздела не читает и не переписывает persisted
`mode`. Сам текущий
глобальный режим виден отдельной read-only строкой над матрицей
(`demoStore.mode` через `b-tag`) только для справки. Старое демо приоритета
`ListAsyncState` (loading &gt; error &gt; empty &gt; no-results) остаётся
отдельным блоком со своими локальными переключателями — оно не входит в
матрицу и не дублирует её разметку, а иллюстрирует то, что сама матрица не
показывает: поведение компонента при одновременно включённых флагах.

### Опциональное resource-меню Navbar (Task A8.1)

Полный Navbar (не `minimal`) больше не содержит глобальную строку поиска —
разметка и `ToolbarSearch` были удалены из `Navbar.vue`; `ToolbarSearch` сам
остаётся общим компонентом и продолжает демонстрироваться на
`/kit/navigation-states` (`components/kit/NavigationStates.vue`), это не
касается его контракта.

Resource links (`.tr-topbar__links` в desktop-виде, `.tr-user-resource*` в
mobile/user-представлении) читаются из **одного** вычисляемого реестра
`resourceLinks` в `Navbar.vue`, ключ которого — kit-only
`useDemoStore().resourceMenuSize` (`none | compact | full`,
`RESOURCE_MENU_SIZES`/`RESOURCE_MENU_SIZE_LABELS` в `src/stores/demo.js`,
persisted тем же `trickster-demo-state`, невалидное/отсутствующее сохранённое
значение нормализуется в `"compact"`):

- `none` → пустой массив — `<nav class="tr-topbar__links">`, разделитель
  `.tr-user-resource-separator` и сами пункты `.tr-user-resource` не
  рендерятся вовсе (`v-if="resourceLinks.length"` в обоих местах разметки),
  поэтому ни резервируемого зазора, ни пустого узла не остаётся в DOM ни в
  одной проекции Navbar;
- `compact` (значение по умолчанию) → базовый набор из трёх пунктов
  («Новости», «API», «Документация»), совпадающий с прежним хардкодом;
  `full` → тот же набор плюс «Поддержка» и «Сообщество», чтобы без правки
  кода проверить более широкий Navbar.

Второй, захардкоженный набор ссылок для desktop/mobile-user представлений не
заводится — оба места разметки перебирают один и тот же `resourceLinks`.
Маршрутные `NavbarTabs`/слот `menu` не зависят от размера resource-меню и
продолжают отображаться независимо от него, в том числе при `none`.

Это, как и остальная демо-панель, **не часть контракта кабинета** — kit-only
переключатель для проверки дизайна на всех размерах реестра, не переносится в
`get.3xtr.im`.

### Уведомления Navbar (только кит, Task A8.2)

Колокольчик `.tr-notifications-trigger` и его дропдаун
`.tr-notifications-dropdown` — не всегда видимый элемент Navbar, а прямая
проекция изолированного `useNotificationsStore()`
(`src/stores/notifications.js`), keyed по активному `workspace` (id, который
`Navbar.vue` получает как проп/`v-model` — сам стор про
`useWorkspaceStore()` не знает, только принимает id аргументом):

- `<b-dropdown class="tr-notifications-dropdown">` (desktop) и пункт
  «События» в `tr-mobile-nav` рендерятся тогда и только тогда, когда
  `notificationsStore.unreadCountFor(workspace)` больше нуля
  (`hasUnreadNotifications` в `Navbar.vue`) — при пустом или неизвестном id
  пространства (в т.ч. только что созданного `createWorkspace()`) фикстура
  по умолчанию не несёт уведомлений, поэтому control не рендерится вовсе;
- badge на триггере, aria-label («События: N непрочитанных») и заголовок
  дропдауна («N новых») всегда показывают фактическое
  `unreadCountFor(workspace)` — нулевое значение не подменяется статикой,
  оно просто скрывает весь control;
- клик по строке уведомления вызывает `markRead(workspace, id)`, а «Все
  события» — `markAllRead(workspace)`; оба реактивно обновляют то же
  fixture-состояние без перезагрузки, и когда непрочитанных становится 0,
  колокольчик исчезает сам по следующему рендеру.

Это kit-only fixture-контур: без API, polling, real-time транспорта и
persistence — при перезагрузке кита фикстура возвращается к исходному
набору. `docs/agent-migration-guide.md` не описывает этот store: реальные
уведомления в `get.3xtr.im` остаются отдельной, не координированной здесь
задачей (см. «Backend changes» в `CLAUDE.md`).

### История уведомлений, помощь и аудит пространства (Task A10.8)

Три постоянных, route-backed поверхности над уже существующими данными — ни
одна не дублирует и не заменяет колокольчик `Navbar.vue` (Task A8.2) выше:

- **`/profile/notifications` (`notification-history`,
  `src/components/profile/NotificationHistory.vue`)** — персональная лента
  над тем же `useNotificationsStore()`, доступная и когда колокольчик скрыт
  (нулевой unread). Переключатель «Все/Непрочитанные», пагинация `b-pagination`
  (5 записей на страницу), кнопка «Отметить все как прочитанные». Read
  теперь per-recipient (`WorkspaceNotification.readBy: string[]`,
  `DEFAULT_RECIPIENT_ID = "me"`) — прочтение одного получателя не трогает
  чужое `readBy`, и запись никогда не удаляется. `markAllRead` — snapshot-
  операция: она проходит по уже загруженному на момент вызова списку, а не
  по будущим уведомлениям (`receiveNotification` — kit-only helper,
  используемый только тестами, чтобы это продемонстрировать, без реального
  push-механизма). Каждая запись может нести `target` —
  `{ available: true, to }` рендерится ссылкой, `{ available: false }` —
  текстом «Материал недоступен» (удалённая/недоступная цель), запись без
  `target` — только текст. Демо-контракт как у `workspace/Members.vue`
  (`Loader`/`AsyncState`/`ListAsyncState`), плюс отдельная проверка
  `demoStore.isError` перед самим действием «Прочитано»/«Отметить все» —
  ошибка чтения списка и ошибка read различаются, а не смешиваются в одно
  состояние. Текст ниже списка отдельно объясняет retention (30 дней) и
  прямо говорит, что это не полный аудит, со ссылкой на «Аудит» ниже, когда
  он доступен текущей роли.
- **`/profile/help` (`help`, `src/components/profile/Help.vue`)** — статичный
  глоссарий терминов (Агент/Песочница/Знания/Пространство, без переименования)
  и список типовых сценариев исправления (см. `.plan` Stage A10, пункт 9).
  Не читает никакой стор — тексту нечего загружать/ошибаться/пустеть.
- **`/workspace/audit` (`workspace-audit`, `src/components/workspace/Audit.vue`,
  API Issue #109)** — история изменений владельцев, участников, доступов и
  настроек, отдельная от персональной ленты выше. Видимость — по роли
  активного пространства: `useWorkspaceStore().canViewAudit(id)` разрешает
  её только `"Владелец"`/`"Администратор"` (`AUDIT_VISIBLE_ROLES`); при любой
  другой роли (например, `"Участник"`) экран показывает `permission-denied`
  **до** проверки глобального demo-режима — недостаточная роль не зависит от
  того, что выставлено в demo-панели. Фикстура (`getAuditLogFor`,
  `src/stores/workspace.js`) несёт только `actor`/`action`/`time`; retention-
  пробел моделируется отдельной записью `{ gap: true, note }`, рендерящейся
  под таблицей, а не строкой внутри неё. Пароли, ключи API и содержимое
  сообщений в этот лог не попадают — новых API producers этот экран не
  реализует (см. `.plan`).

`ProfileShell.vue` получает две новые вкладки («История уведомлений»,
«Помощь») к существующим «Профиль»/«Безопасность»; `Workspace.vue` получает
«Аудит» последней вкладкой к «Обзор»/«Настройки»/«Участники»/«Тариф»/
«Биллинг». `Navbar.vue`'s user-dropdown дублирует «История уведомлений» и
«Помощь» прямыми пунктами — это единственный способ дойти до них без
захода на `/profile` через таб.

### Master-detail и рабочие области

Раздел с постоянным списком слева и содержимым справа строится как
родительский маршрут со списком и вложенным detail-маршрутом, который выводит
содержимое, не размонтируя список. На планшете правая панель свойств
открывается вместо списка; на мобильном list, content и properties доступны
последовательно.

Песочница агента повторяет ту же анатомию, что и диалог — панель чата и
панель свойств внутри общего контейнера, одинаковые заголовки, иконки
действий, оформление сообщений и composer. Обе панели свойств (диалога и
песочницы) открыты **по умолчанию** (`propertiesOpen` стартует `true`), а не
по клику. На ширинах, где обе/все колонки помещаются, панель никак не
закрывается — исчезает только на узком экране, где грид схлопывается в одну
колонку за раз (`is-list-view`/`is-chat-view`/`is-properties-view`, см. раздел
«Master-detail» выше): там в шапке панели остаётся только стрелка влево
(`tr-conversation-properties-action`, без крестика — закрывать в этом виде
нечего, только переключиться на чат/историю), а в шапке чата появляется
шестерёнка (`tr-conversation-settings-action`, `v-if="!propertiesOpen"`),
которая возвращает панель — и снова прячется сама, пока панель открыта.
`AgentPlayground.vue` держит своё `propertiesOpen` локально (не через
provide/inject, в отличие от диалога, где им владеет `Conversations.vue` —
эта страница сама владеет своим гридом, делить его больше не с кем), и в её
панели свойств — только температура и системная инструкция: поля, которые
реально влияют на генерацию в текущей сессии песочницы. Остальные настройки
агента (имя,
статус, модель и BYOK-ключ) остаются во вкладке `NavbarTabs` «Настройки»
(`AgentSettings.vue`) — они ничего не меняют в уже открытой песочнице,
только в самом агенте.

### Navbar и Sidebar

Desktop Navbar содержит логотип, переключатель пространства, действия
пространства, профиль, роль, тему, язык, безопасность, выход и разрешённые
операторские ссылки. Имя пользователя, пространство и тема читаются
реактивно. Отсутствующее значение не подменяется выдуманным. Длинные названия
сокращаются ellipsis, полное значение остаётся доступным.

Sidebar использует Buefy `b-menu` и общий реестр навигации. Ниже `1024px`
статический Sidebar скрывается, а Navbar показывает mobile-modal dropdown.
Блок действий Navbar имеет `margin-inline-start: auto`, поэтому переключатель
пространства остаётся справа даже при отсутствии resource menu и уведомлений.

**W2 — переключатель пространства (Task A10.7).** Единственное личное
пространство не навязывает выбор: триггер и мобильный `b-select` сворачиваются
до второстепенного пункта «Пространство для команды» с плоским текстом вместо
списка/иконки переключения (`Navbar.vue`, `hasMultipleWorkspaces`); клик
только открывает панель с обзором текущего пространства и действием «Создать
пространство» — сам он не выдаёт прав и не создаёт пространство. Как только
пространств больше одного, возвращается обычный переключатель со списком и
всегда обозначенным активным контекстом.

Смена активного пространства и создание нового не применяются на месте —
`App.vue` сначала переводит на `dashboard`, реиспользуя тот же
`useDirtyExitGuard` (`onBeforeRouteLeave`), что и любая сохраняемая форма
кита: грязная форма показывает свой диалог «Сохранить / Выйти без сохранения /
Остаться», и выбор «Остаться» отменяет переключение, а не применяет его под
несохранённым вводом. Успешная навигация на `dashboard` попутно освобождает
любой per-screen selection/filter (компонент размонтируется), так что старый
контекст не переживает переключение пространства.

### Mobile navigation

Ниже `1024px` dropdown Navbar — единственная навигационная поверхность. В нём
доступны переключатель пространства, основная и административная навигация,
профиль, безопасность, выход, тема и язык.

Обязательный keyboard-контракт:

- burger и close — нативные `<button type="button">`;
- Buefy `mobile-modal` (через собственную директиву `trap-focus`) держит Tab
  внутри панели и закрывает её по Escape, но не возвращает фокус триггеру —
  этот разрыв закрывает `useFocusTrap` (`src/composables/useFocusTrap.js`),
  подключённый в `Navbar.vue` к обеим `mobile-modal`-панелям
  (`tr-mobile-nav`, `tr-user-dropdown`): при закрытии панели любым способом
  (Escape, клик по пункту, клик вне) фокус возвращается на элемент, с
  которого было открыто меню;
- переходы выполняются по реальным URL из общего реестра;
- переключатели темы имеют доступное имя через label или `aria-labelledby`.

`AsyncState` и его обёртка не выполняют запросов и не принимают
permission-решений. Вариант `error` использует `role="alert"` и assertive live
region; `empty`/`no-results`/`permission-denied` — `role="status"` и polite.
Вариант `loading` не ставит `role`/`aria-live` на сам `.tr-async-state` —
эту семантику несёт вложенный `Loader` (`role="status"`, `aria-live="polite"`,
`aria-label="Загрузка"`), чтобы не дублировать одну и ту же live-region
дважды. Разметка `.tr-async-state--error` в любом кит-экране, собранном не
через `AsyncState` (легаси до миграции), обязана нести
`role="alert"`/`aria-live="assertive"` сама, см. `agent-migration-guide.md`,
раздел 9.

### Собственный компонент или Buefy

Если Buefy покрывает элемент, используется Buefy; собственный компонент не
пишется и ручная Bulma-разметка не собирается.

| Элемент | Штатный компонент |
|---|---|
| Кнопка | `b-button` |
| Поле формы | `b-field` + `b-input` / `b-select` / `b-checkbox` / `b-switch` |
| Секретное поле | `b-input type="password" password-reveal` |
| Таблица | `b-table` (мобильный режим — `mobile-cards`) |
| Пагинация | `b-pagination` |
| Модальное окно | `b-modal` |
| Подтверждение | `b-dialog` |
| Боковая панель | `b-sidebar` |
| Тост | `b-toast` |
| Баннер | `b-message` |
| Загрузка поверх контента | `b-loading` |
| Скелет | `b-skeleton` |
| Прогресс | `b-progress` |
| Загрузка файлов | `b-upload` |
| Переключение контента вкладками | `b-tabs` |

Единственное обоснованное исключение — `NavbarTabs`: `b-tabs` переключает
контент, а не маршрут, и не умеет жить в навбаре через Teleport.

Собственный компонент допустим, только когда у Buefy нет подходящего. Такое
решение фиксируется здесь с обоснованием, а не принимается по месту.

### Store-API для оверлеев и уведомлений

Task A4.5. `src/stores/modal.js` (`useModalStore`) и `src/stores/toaster.js`
(`useToasterStore`) — тонкие Pinia-адаптеры над программным API Buefy, а не
собственные `Modal.vue`/`ConfirmDialog.vue`/`Toaster.vue`: экраны продолжают
рендерить `b-modal`/`b-sidebar` в своей разметке, но открытым/закрытым
состоянием управляет общий store по строковому ключу вместо локального `ref`
на каждом экране.

- `useModalStore().isOpen(id)` / `.open(id)` / `.close(id)` / `.toggle(id)` —
  состояние конкретного `b-modal`/`b-sidebar`, привязывается через
  `:model-value` + `@update:model-value` (ключи — произвольные строки уровня
  экрана, например `"knowledge-collection-form"`, `"uikit-sidebar"`).
- `useModalStore().confirm(options)` — тонкая обёртка над `b-dialog`
  (`DialogProgrammatic.confirm`); у подтверждения нет декларативной разметки
  на экране, поэтому ключ не нужен.
- `useToasterStore().open(options)` / `.success(message)` / `.error(message)`
  / `.info(message)` — обёртка над `b-toast` (`ToastProgrammatic`).

Escape, focus-trap/return и scroll-lock обеспечивает сам Buefy; слои overlay
согласованы с `--tr-z-modal`/`--tr-z-sidebar`/`--tr-z-toast` (см. «Z-index и
stacking» выше) — сторы не вводят собственных значений `z-index`. Используется
в `kit/DialogsOverlays.vue` (демо-модалка, боковая панель, диалог
подтверждения, тост) и `Knowledge.vue` (модалка создания коллекции). До
Task A9.2 `Agents.vue` тоже держало здесь свою локальную модалку создания
агента — она удалена: единственный вход в создание агента теперь ведёт в
route-driven мастер (`agents/AgentWizard.vue`), а не в отдельную форму, см.
«Мастер создания агента: точки входа» ниже.

### Демо-поток загрузки файлов

Task A4.6. Секция «Загрузка файлов» в `kit/Forms.vue` показывает очередь, прогресс,
успех и ошибку на `b-upload` без сети и без собственного компонента загрузки —
`FileUpload`/`FileList`/`FileListItem` из `get.3xtr.im` в ките не
воспроизводятся.

- `b-upload` (`drag-drop`, `expanded`) только принимает файл в очередь;
  сама загрузка — локальная fixture-state machine (`uploadQueue`,
  `resetUploadDemo()`, `runUploadDemoStep()` в `kit/Forms.vue`), без `fetch`/`axios`
  и без persistence.
- Состояния очереди: `queued` → `uploading` (таймер увеличивает `progress` на
  25% каждые 400 мс) → `success` или `error` — воспроизводятся детерминированно
  при загрузке страницы и повторяются кнопкой «Повторить демо».
- Прогресс отображается через `b-progress`, итог — через `b-message`
  (`is-success`/`is-danger`); отдельного компонента прогресса или баннера кит
  не заводит.
- Файл, добавленный через `b-upload` вручную, встаёт в очередь тем же
  механизмом и завершается успехом либо ошибкой поочерёдно — это иллюстрация
  потока, а не реальная валидация файла.

## Формы

Стандартная форма:

```text
.tr-form
├── b-field (label, help, message, type="is-danger")
│   └── b-input / b-select / b-checkbox / b-switch
└── .tr-form__footer
```

`.tr-form` отвечает только за раскладку — сетку полей, футер и опасную зону.
Label, подсказка, сообщение об ошибке и состояние ошибки — штатные
возможности `b-field`.

Правила:

- label программно связан с контролом;
- required обозначается не только цветом;
- ошибка валидации находится рядом с контролом и доступна скринридеру;
- секретное поле раскрывается штатным `password-reveal`;
- disabled и loading заметны визуально и программно;
- опасные действия отделяются от обычного submit;
- футер переносится на узких экранах без overflow.

### Fixture-контракт сохранения и dirty-exit (Task A10.1)

`WorkspaceSettings.vue`, `profile/Settings.vue`, `knowledge/Settings.vue` и
`AgentSettings.vue`'s секция «Модель и собственный ключ» — четыре независимых
формы-транзакции (конфигурация пространства/коллекции, профиль, ключ агента);
ни одна не становится частью другой. Каждая теперь строится на двух общих
composables вместо повторения локального `draft`/`hasChanges`/`save`/`reset`:

- **`composables/useSavableForm.js`** — состояния `clean → dirty → pending →
  success | error | conflict | unknown`. Без сети: «конфликт» — это не
  случайная имитация, а честная проверка дрейфа канонической fixture-записи
  (`source()`) между последней синхронизацией драфта и моментом `save()` —
  если она изменилась (другой экран/composable успел её мутировать), это и
  есть конфликт. «Unknown» — то же самое честно: если `submit()` не
  разрешился за `pendingTimeoutMs`, `verify()` дожидается того же
  in-flight-промиса вместо повторной отправки потенциально уже применённой
  команды. Повторный `save()` во время `pending` не создаёт второй эффект —
  вызывающий получает тот же промис. `retry()` работает только из `error`;
  `unknown` требует `verify()`, а не слепой повтор. При конфликте
  `reloadRemote()` перечитывает актуальное значение (драфт отбрасывается),
  `keepLocal()` сохраняет локальный ввод и лишь обновляет базовую точку
  сравнения — автоматической перезаписи чужого изменения нет ни в одном из
  путей. Поле `fieldErrors` совмещает живую валидацию (видна сразу, до
  нажатия «Сохранить») и ошибки последнего `submit()` (например,
  серверные/fixture-специфичные) — первая имеет приоритет.
- **`composables/useDirtyExitGuard.js`** — dirty-exit guard для роутинга
  (`onBeforeRouteLeave`) и закрытия вкладки (`beforeunload`). Диалог
  «Сохранить / Выйти без сохранения / Остаться» (`common/DirtyExitModal.vue`,
  тот же `.modal-card`/`b-modal`-паттерн, что `channels/TakeoverModal.vue`)
  блокирует навигацию до явного выбора; «Сохранить» отпускает переход только
  если `onSave()` реально вернул успех — ошибка или конфликт оставляют форму
  открытой, а не молча продолжают переход.
- **`common/FormErrorSummary.vue`** — сводка ошибок формы: каждая ошибка —
  настоящая `<button>` внутри `b-message type="is-danger"`, поэтому она
  доступна с клавиатуры (Tab доходит, Enter/Space переводит фокус на само
  поле по `id`). Это не замена сообщения об ошибке у самого поля
  (`b-field`'s `type`/`message`), а дополнительный переход к первой ошибке.

Формы, которые остаются immediate-apply (имя/статус агента, переключатели
уведомлений профиля), эту пару composables не используют — они не имеют
границы отмены/подтверждения и ничего не удаляют, поэтому явный
save/dirty-guard для них избыточен.

### Мгновенные команды vs сохраняемая форма (Task A10.2)

`.plan` Stage A10 «Явное сохранение и безопасное редактирование»: пауза,
перехват канала, отвязка ключа и удаление ключа/канала применяются сразу,
своим вызовом стора — ни одна из них не проходит через `useSavableForm`'s
`draft`/`save()` и не требует, чтобы форма была dirty. Нажатие «Сохранить»
в любой из форм A10.1 не выполняет ни одну из этих команд, и ни одна из них
не требует «Сохранить» — этим они отличаются от «Отвязать ключ»/«Удалить
ключ», которые внешне похожи на сохранение, но именно потому и не им
являются:

- **Пауза/резюме канала** (`ChannelCard.vue` → `deactivateChannel`/
  `activateChannel`) — без confirm: обратимо повторной активацией, не
  стирает данные.
- **Перехват (handoff) канала** (`TakeoverModal.vue` → `confirmTakeover`) —
  собственное модальное подтверждение, отдельное от каталога каналов.
- **Отвязать ключ от агента** (`AgentSettings.vue` → `agentsStore.detachApiKey`,
  см. «Настройки агента» ниже) — подтверждение, применяется к одному
  агенту, ключ остаётся в воркспейсе.
- **Удалить ключ** (`ApiKeySelect.vue` → `apiKeysStore.deleteKey`, см. «Ключи
  API» ниже) — подтверждение называет затронутых агентов по имени, стирает
  сам ключ безвозвратно.
- **Удалить канал** (`ChannelsView.vue` → `channelsStore.deleteChannel`) —
  подтверждение перед удалением с текстом «без возможности восстановления»,
  без выдуманного каскада (`.plan`: «не показывать выдуманный каскад или
  обещание Undo, если реальной обратной операции нет»).

Различие между «удалить ключ/канал» и «отвязать» всегда формулируется в
терминах реальных fixture-последствий (что исчезает навсегда, кого это
затрагивает), а не общей фразой «действие нельзя отменить».

**Название и статус (Stage A10 review fix)** — раньше immediate-apply
`v-model` прямо в стор, что противоречило Stage A10 «Явное сохранение и
безопасное редактирование» (правки действующего агента применяются только
явным Save, а несохранённый ввод не теряется без выбора). Разделены по тому,
чем реально являются:
- **«Название»** — независимый от модели/BYOK `useSavableForm` draft
  (`.todo`: «Независимые операции... не становятся одной транзакцией»), с
  собственными Save/«Отменить изменения», field-ошибкой на пустое значение
  и `agentsStore.renameAgent` как точкой сохранения.
- **«Статус»** — не форма: набор мгновенных lifecycle-команд (кнопки на
  остальные `AGENT_STATUSES`, кроме текущего), каждая со своим
  `modalStore.confirm`, называющим реальное последствие (например,
  приостановка — «агент перестанет отвечать на новые сообщения»), и
  `agentsStore.setAgentStatus` как применением — тот же паттерн, что уже
  существующая «Отвязать ключ» ниже. Это реализует intent Task A10.2 про
  pause/resume как отдельную команду, которого раньше не существовало в виде
  контрола вообще.

Единый `dirtyGuard` внизу страницы объединяет dirty-exit сразу для обоих
draft'ов (название и модель/ключ) одним диалогом «Сохранить / Выйти без
сохранения / Остаться» — каждый draft при этом сохраняется своим независимым
`submit()`/store-вызовом, так что ошибка одного не блокирует и не
маскирует успех другого.

- **Раздельные контролы для обычной и BYOK-модели.** Экран держит два
  независимых `ModelSelect`: один для обычной модели (`agent.model`,
  показывается, пока BYOK выключен), другой — для BYOK (`agent.byok_model` +
  `agent.provider_model_id`, ограничен OpenRouter, показывается, пока BYOK
  включён). Переключатель `b-switch` меняет только то, какой из двух виден;
  ни один не перезаписывает другой. Из этого следует, что выключение BYOK
  всегда автоматически возвращает ранее выбранную обычную модель — без
  какой-либо логики отката, просто потому что `agent.model` не участвовал в
  BYOK-ветке. До этого исправления оба режима делили одно поле `model`, из-за
  чего включение BYOK могло молча сохранить агента с моделью не из
  OpenRouter — это было устранено ревью Stage A6 (см. Task A6.3 evidence в
  `.plan`).
- **Нельзя сохранить включённый BYOK без ключа и без модели.** Ревью Stage A6
  указало, что до этого исправления `AgentSettings.vue` позволяла сохранить
  агента с `use_own_api_key: true`, но без ключа и без выбранной модели —
  переключатель включён, а исполнять запрос нечем. Теперь кнопка «Сохранить
  модель и ключ» заблокирована, пока `draft.useOwnApiKey` истинен, а ключ
  (`draft.apiKeyId`) или модель (`draft.byokModel`/`draft.providerModelId`)
  не выбраны — оба поля рядом с `ModelSelect`/`ApiKeySelect` переключаются в
  `b-field type="is-danger"` с текстом ошибки. Правило продублировано в
  `stores/agents.js#isByokSaveValid` и применяется как защитный, а не
  основной рубеж внутри `updateAgentSettings` — не полагается только на то,
  что интерфейс не даст нажать кнопку.
- Ключ выбирается из сохранённых в воркспейсе через `ApiKeySelect` (см. выше)
  — инлайн-поля для ввода текста ключа в этом экране больше нет.
- Переключение BYOK (`b-switch`) сразу показывает инлайн `b-message`
  (`type="is-warning"`) с последствиями: при включении — модель и ключ
  выбираются заново из отдельных контролов, ограниченных OpenRouter, а
  обычная модель никуда не денется; при выключении — ключ, `byok_model` и
  `provider_model_id` будут удалены (обычная модель не затрагивается).
  Сообщение появляется, пока состояние переключателя отличается от
  сохранённого, и пропадает, если пользователь вернул переключатель обратно.
- Нажатие «Сохранить модель и ключ» вызывает `useModalStore().confirm()`
  (`b-dialog`) только тогда, когда сохранение действительно удалит ключ —
  единственный такой случай теперь выключение BYOK (пока BYOK включён,
  сохранение возможно только с уже выбранным ключом — смена ключа на другой
  сохранённый просто перепривязывает `has_api_key`, ничего не стирая).
  Отмена в диалоге не меняет сохранённого агента и не вызывает мутацию;
  подтверждение вызывает `updateAgentSettings` и, если сервер (fixture)
  вернул `api_key_cleared`, показывает это тостом вместо тихого исчезновения
  ключа.
- Выключение BYOK всегда очищает `byok_model`, `provider_model_id` и ссылку
  на ключ (`api_key_id`) — все три поля действительны только вместе с
  собственным ключом (Stage A6 решение 3).
- **«Отвязать ключ» (Task A10.2)** — отдельная мгновенная команда под
  футером формы (`.tr-agent-settings__detach`), видна, пока у агента
  `has_api_key`. Применяется сразу через `agentsStore.detachApiKey`, в обход
  `draft`/«Сохранить модель и ключ»: не часть транзакции формы модели и не
  требует, чтобы форма была dirty. Своё подтверждение через
  `modalStore.confirm`. Затрагивает только текущего агента — ключ остаётся
  в `apiKeysStore` для остальных (в отличие от «Удалить ключ» в
  `ApiKeySelect`, см. выше). Если форма модели была dirty в момент отвязки,
  расхождение всплывает обычным конфликтом `useSavableForm` при следующем
  «Сохранить», а не тихо перезаписывается — тот же контракт conflict, что и
  у стороннего изменения из другого окна.
- **Платформенная оплата и BYOK объясняются раздельно (Task A10.6).** Под
  переключателем `b-switch` — одна строка `tr-muted`, которая меняется вместе
  с `draft.useOwnApiKey`: включённый BYOK говорит, что ответы оплачивает
  напрямую провайдер ключа, отдельно от лимитов и тарифа пространства;
  выключенный — что ответы через каталожную модель платформы учитываются в
  тех же лимитах/тарифе. Это разграничение «кто платит», а не оценка
  стоимости — у кита нет серверных данных о цене ответа ни для одного из
  режимов, и оба пояснения explicitly избегают прогноза/суммы (см.
  «Семиключевой контракт ресурсов и лимитов» ниже). `workspace/WorkspaceBilling.vue`
  зеркалит ту же мысль на вкладке «Биллинг».
- **`byok_model` — предложение к серверному контракту, не факт его
  существования.** Как и `provider_model_id`, поле `byok_model` реализовано в
  ките полностью как fixture, опережающая контракт (см. «Backend changes» в
  `CLAUDE.md`): в кабинете `get.3xtr.im` такого поля пока нет. Комментарии в
  `AgentSettings.vue`/`stores/agents.js` ссылаются на
  [api.3xtr.im#112](https://github.com/iam3xtr/api.3xtr.im/issues/112) как на
  место, где стоит расширить контракт полем для отдельного хранения
  BYOK-модели (в дополнение к уже обсуждаемому там `provider_model_id`) —
  это предложение к будущей доработке API, а не описание уже реализованного
  поведения `api.3xtr.im`.

### Знания агента после мастера (`AgentKnowledge.vue`, Task A10.3)

Четвёртая вкладка детали агента, `/agents/:id/knowledge`, наравне с
«Песочница»/«Настройки»/«Каналы» (`AgentDetail.vue`). Продолжает тот же
простой путь, что шаг «Знания» мастера (Task A9.4, см. выше) — без выбора
коллекции, embedding-профиля или chunk parameters; общие коллекции и связи
нескольких агентов остаются экспертным сценарием раздела «Знания»
(`components/knowledge/**`), не переименованным и не заменённым этой
вкладкой.

- **Durable-ссылка, а не draft.** `stores/wizard.js` держит не более одного
  draft'а на пространство — второй агент, чей мастер запущен в том же
  пространстве, тихо вытеснил бы ссылку на коллекцию первого. Поэтому ссылка
  живёт на самом агенте: `agent.knowledgeCollectionId` (`stores/agents.js`).
  `wizardStore.finalizeAgentFields` переносит туда `draft.resources.collectionId`,
  как только агент точно существует (идемпотентно через
  `agentsStore.linkKnowledgeCollection`); эта же вкладка заводит ссылку сама
  для агента, который никогда не проходил шаг «Знания» мастера (фикстура или
  прерванный draft) — лениво, при первом добавленном материале, тем же
  приёмом, что `KnowledgeStep.vue`. Повторный визит всегда резолвит
  коллекцию по этому id, а не создаёт вторую.
- **Тот же add/list UI, что шаг мастера.** Верстка и CSS переиспользованы
  дословно (`.tr-wizard-source*`, раздел «15. Wizard» `trickster-buefy.scss`):
  `b-upload` drag-drop для файлов, «Добавить текст»/«Добавить ссылку» —
  инлайн-форма, список материалов с тегом статуса и действиями
  «Повторить»/«Заменить»/удалить.
- **Фазы материала:** `upload` (источник ещё не стал fixture-объектом,
  чисто клиентское состояние без стабильного id) → `processing`
  (`KnowledgeObject.status === "indexing"`) → `ready`/`error`
  (`indexed`/`error`, тот же таймер-конвенция «каждый третий — ошибка»).
  Статус вне этого набора рисуется как `unknown` (отдельный, не «зелёный»,
  тег), а не молча подменяется «готово». Сводка коллекции сверху отдельно
  различает `ready` (все материалы готовы) от `partial` (готовы частично) —
  так частично обработанная коллекция не выглядит полностью пригодной для
  ответов. `limit` (материал не обработан из-за тарифного лимита количества/
  размера) — заявленное, но не реализованное измерение: у кита нет ни одного
  стора с такой цифрой (`stores/workspace.js` знает только про кредиты и
  диалоги), а придумывать тарифный лимит здесь означало бы придумывать
  непродуктовое решение произвольно на этапе вёрстки.
- **Три разных действия удаления**, каждое — своя команда:
  - «Удалить материал» — мгновенно (без confirm, как в
    `knowledge/Files.vue`), убирает один объект из коллекции агента, не
    трогая коллекцию и других агентов.
  - «Убрать из знаний агента» — коллекция и её материалы остаются в разделе
    «Знания» (`knowledgeStore` не тронут), только `agent.knowledgeCollectionId`
    обнуляется (`agentsStore.unlinkKnowledgeCollection`). Свой confirm
    называет агента по имени.
  - «Удалить коллекцию» — стирает коллекцию и все её материалы безвозвратно
    для каждого агента, который на неё ссылается; confirm называет всех
    затронутых агентов по имени (`agentsStore.listAgentsUsingCollection`),
    тот же приём, что `ApiKeySelect.vue`'s «Удалить ключ» (Task A10.2).
    Ни один из трёх сценариев не выходит за пределы своей коллекции/агентов.
- **Подсказка вернуться в песочницу.** Пока в коллекции есть хотя бы один
  материал, под списком — ссылка на `/agents/:id` (вкладку «Песочница»)
  предложить задать вопрос заново; обновление источника не выдаётся за
  гарантию правильного ответа или обнаруженных пробелов.

## Состояния и доступность

- Смысл статуса или действия не кодируется только цветом.
- Все интерактивные элементы доступны через Tab и имеют заметный
  `:focus-visible`.
- Для контрола предпочтителен нативный `button`, `a[href]`, `input`, `select`
  или `textarea` вместо ARIA-эмуляции.
- Скелеты и переходы учитывают `prefers-reduced-motion: reduce`.
- Интерфейс поддерживает 200% zoom и ширину от `360px`; горизонтальный
  overflow допустим внутри обёртки таблицы или специализированной рабочей
  области.
- Декоративная иконка имеет `aria-hidden="true"`; смысловая кнопка получает
  доступное имя независимо от иконки.

## Z-index и stacking

Единственный источник значений — токены `--tr-z-*`, объявленные один раз в
`:root` (`trickster-buefy.scss` § 1. Tokens; Sass-константы — в
`_trickster-tokens.scss`, секция «Z-index scale»). Слои не зависят от темы, и
`$dropdown-content-z`/`$modal-z` Bulma конфигурируются теми же константами,
поэтому `b-dropdown`, `b-select`, `b-autocomplete` и `b-modal` попадают в ту
же шкалу автоматически. Произвольный `z-index`-литерал в ките не допускается:
локальное поднятие элемента над непосредственным соседом внутри его же
stacking context выражается как `calc(var(--tr-z-content) + N)`, а не число
само по себе.

| Слой | Токен | Значение | Владелец | Статус |
|---|---|---:|---|---|
| Обычный контент | `--tr-z-content` | 0 | Feature views | реализован |
| Sticky topbar | `--tr-z-sticky-header` | 20 | `.tr-app > .tr-topbar` | реализован |
| Подложка/backdrop (drawer, модалка, диалог) | `--tr-z-overlay` | 29 | `.sidebar-overlay`, локальные backdrop внутри собственного stacking context | `.sidebar-overlay` — **CSS отсутствует** |
| Sidebar: десктопная колонка и выдвижная панель | `--tr-z-sidebar` | 30 | `.tr-sidebar`, `.sidebar-column` | `.tr-sidebar` реализован; `.sidebar-column` (мобильная выдвижная панель) — **CSS отсутствует** |
| Dropdown | `--tr-z-dropdown` | 35 | Bulma/Buefy `dropdown-content` (`b-dropdown`, `b-select`, `b-autocomplete`) | реализован через конфигурацию Bulma |
| Модальное окно | `--tr-z-modal` | 40 | Buefy `.modal` (`b-modal`) через `$modal-z` | реализован через конфигурацию Bulma |

Dropdown остаётся над локальным содержимым (включая sidebar и topbar), но
ниже слоя модального окна.

`.copy-pre__button` поднимается над своим прямым соседом (содержимым `<pre>`)

context (`.copy-pre`) — это не отдельный слой шкалы, а локальное
упорядочивание внутри уже позиционированного родителя. Модалка, диалог,

штатные `b-modal`/`b-dialog`/`b-sidebar`/`b-toast`, см. «Собственный компонент
или Buefy».

## Content patterns

Эталонные фрагменты разметки для каждого паттерна — в
[`agent-migration-guide.md`](agent-migration-guide.md). Здесь — только
правила выбора паттерна.

### Списки: каталог карточек или таблица

**Каталог карточек** (`tr-catalog` / `tr-catalog-grid` / `tr-entity-card`) —
когда запись имеет неоднородный или богатый состав: иконка сущности, статус,
описание, набор условных действий, и вся карточка кликабельна целиком.
Типичные представители: агенты, коллекции знаний, каналы.

**Таблица** (`b-table`) — когда записи однородны по набору полей и читаются
построчно: участники, приглашения, пользователи, провайдеры, модели, логи
запросов. Мобильный режим — штатный `mobile-cards` (не `.tr-table--stack`,
см. ниже). Оформление задаётся один раз для `.b-table` в
`trickster-buefy.scss`; частные случаи — модификаторы на корневом
`<b-table class="tr-table--compact">` / `<b-table class="tr-table--breakdown">`,
а не новый компонент или ручная разметка. Эталон — таблицы в `Dashboard.vue`,
`Knowledge.vue` и раздел «Таблица» в `kit/Tables.vue`.

Создание нового объекта в каталоге может рендериться последней карточкой
грида (`tr-entity-card--create`) — это визуальный, а не структурный элемент;
приложение вправе оставить кнопку создания в заголовке страницы.

Агрегированный итог по каталогу (общий размер, общее число) выносится
отдельным блоком вне грида, а не строкой внутри него.

### Toolbar

Поиск, фильтры и действия над списком живут в одном контракте
`.tr-page-toolbar` с областями поиска, фильтров и действий, собранном
компонентом `Toolbar` (`src/components/common/Toolbar.vue`, Task A4.7):
`v-model:search` проксируется во внутренний `ToolbarSearch` (сохраняет
`Ctrl/⌘ K` и `kbd`-подсказку), слот `filters` — набор `ToolbarDropdown`, слот
`actions` (или `default`) — кнопки действий. Ниже брейкпоинта инлайновые
пилюли-фильтры скрываются, и тот же слот `filters` рендерится ещё раз внутри
`MobileFilters` — это не вторая строка toolbar, а единственный способ
добраться до фильтров на узком экране; проп `filters-active` пробрасывает
признак «есть активный фильтр» на триггер `MobileFilters`, так как сам
`Toolbar` не видит состояние слота.

Собственные toolbar-классы под конкретную страницу не заводятся.

### Пустые состояния

Контент-блок — `.tr-async-state`, ограниченный пятью модификаторами:
`--loading`, `--empty`, `--no-results`, `--error`, `--permission-denied`
(эталонная разметка и правила по каждому — `agent-migration-guide.md`,
раздел 9). Различаются ровно два практических случая на текущих экранах
кита:

- **вся страница пуста** — `.tr-async-state.tr-async-state--empty`, для
  полностраничного варианта — в обёртке `.tr-section-empty` (чистый
  sizing-wrapper без собственной content-стилизации), с предметной CTA;
- **пусто из-за фильтра или поиска** — `.tr-async-state.tr-async-state--no-results`,
  а для каталога карточек — `.tr-catalog-empty` внутри грида.

Третьего варианта не заводится, ветки `error` и `permission-denied` при этом
не теряются — они часть того же CSS-контракта и не выражаются собственными
классами.

### Панели настроек

Паттерн `tr-settings__panel` — самостоятельный список опций-переключателей без
обязательных текстовых и числовых полей. Страница, где переключатели
перемешаны с обязательными полями и сохраняются одной транзакцией, — это
форма, а не панель настроек, и остаётся на форм-контракте.

   потребителя (эта панель не рисует отдельный page-level `<h1>` и не
   копит изменения под одну кнопку сохранения — каждый `b-switch`
   применяется сразу) и удалены из `trickster-buefy.scss` задачей A5.11,
   закрывающей Stage A5 — сама эта задача и есть тот «будущий таск», на
   который ссылалась предыдущая пометка. Транзакционный save-ряд на панели
   настроек, если понадобится позже, переиспользует `.tr-form__footer`, а не
   восстанавливает `.tr-settings__panel-footer`. `.tr-settings`/
   `.tr-settings__panel` потребителя не теряют — их использует и
   `WorkspaceSettings.vue`, и
   `AgentSettings.vue`/`knowledge/Settings.vue`/
   `profile/{Settings,Security}.vue`.
   `tr-tariff-selector__card--current`, ранее числившийся кандидатом на
   исключение, уже используется `TariffSelector.vue` (кит и приложение) и под
   эту пометку не подпадает.
2. **`<Компонент>.vue foundation (get.3xtr.im component, no kit equivalent)`**
   — CSS для компонента `get.3xtr.im`, который Stage A4 сознательно не
   переносит в кит (`PaginationControls`, `SkeletonLoader`, `ProgressBar`):
   `.plan` (Stage A4, «Что сделать») заменяет их в ките штатными
   `b-pagination`/`b-skeleton`/`b-progress`, поэтому у `.pagination-controls*`
   (`trickster-buefy.scss`), `.skeleton-loader*` и `.progress-bar*` нет и не
   будет кит-компонента-потребителя — CSS остаётся только ради 1:1 sync в
   `get.3xtr.im`, где одноимённые `.vue`-компоненты уже существуют и
   используют эти классы. Такие правила не считаются мёртвым CSS. Прежде эта
   же пометка временно означала «Stage A4 target component» для компонентов,
   которые Stage A4 действительно перенёс: `PageHeader` (`.tr-page-header`,
   `.page-header__*`) и `CopyPre` (`.copy-pre*`) реализованы задачей A4.2,
   `AsyncState`/`ListAsyncState` (`.tr-async-state*`, `.tr-section-empty`) —
   задачей A4.4, `Toolbar`/`ToolbarSearch`/`ToolbarDropdown`/`MobileFilters` —
   задачей A4.7, `NavbarMenu`/`NavbarTabs` — задачей A4.3; у всех них пометка
   снята, классы имеют явного потребителя в `src/components/common/`.

   Отдельное, не связанное с предыдущим пунктом исключение из требования
   префикса `tr-` из R2 (`.plan`) распространяется на пять семейств:
   `PageHeader` (`.page-header__*`), `PaginationControls`
   (`.pagination-controls*`), `ProgressBar` (`.progress-bar*`),
   `SkeletonLoader` (`.skeleton-loader*`), `CopyPre` (`.copy-pre*`) —
   намеренно используют те же непрефиксированные классы, под которыми
   одноимённые компоненты уже существуют и работают в
   `get.3xtr.im/src/modules/common/components/` сегодня, независимо от того,
   собран ли уже одноимённый компонент в ките. `trickster-buefy.scss`
   синхронизируется в кабинет один в один; переименование этих классов в
   `tr-*` без одновременного переименования самого компонента-потребителя в
   `get.3xtr.im` сломает стилизацию этих живых экранов кабинета при
   ближайшем `ui-kit:update`. Переименование в `tr-*` — задача Stage B4
   (синхронизированная с `get.3xtr.im`), не раньше.

Класс `tr-*`, не подпадающий ни под один из двух пунктов и не встречающийся в
`src/**/*.vue`, — мёртвый CSS и подлежит удалению при следующей правке
затронутой секции файла (раздел 11 `agent-migration-guide.md`).

## Проверка изменений

При изменении контракта проверяется:

- сборка и `lint:style` в ките;
- отсутствие `<style>` в `.vue`-файлах кита;
- отсутствие классов разметки без определения в скомпилированном CSS;
- отсутствие `tr-*`-классов в CSS без потребителя;
- все затронутые экраны кита в светлой и тёмной теме на ширинах `360`, `768`,
  `1024`, `1280` и `1440px`;
- состояния `loading`, `empty`, `no-results`, `error`, `permission-denied`;
- 200% zoom и `prefers-reduced-motion`;
- клавиатурная навигация, Escape, вход и возврат фокуса, Tab containment;
- наложение dropdown, выдвижной панели, модального окна и тостов;
- длинные подписи и длинные названия сущностей.
